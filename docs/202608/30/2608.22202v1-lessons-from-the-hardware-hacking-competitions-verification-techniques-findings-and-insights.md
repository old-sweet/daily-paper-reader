## 摘要
硬件黑客竞赛已成为评估复杂系统级芯片（SoC）设计中安全弱点的实用平台，同时推动了安全意识验证和工具开发。本文通过对开放式硬件黑客竞赛的系统性研究，探讨SoC安全验证，重点关注实际漏洞分析策略、观察到的发现以及安全意识验证的经验教训。我们提出了一种多策略漏洞分析方法，结合了基于仿真的验证、形式验证、lint分析、大语言模型（LLM）辅助的漏洞检测以及覆盖引导的混合模糊测试。通过分析具有代表性的漏洞发现，阐明不同技术如何揭示互补类别的安全缺陷，并总结出面向硅前安全验证的实践教训。最后，我们讨论了竞赛基准如何支持新兴硬件安全技术的可复现评估，并指导未来安全意识的EDA研究。

## Abstract
Hardware hacking competitions have emerged as practical platforms for evaluating security weaknesses in complex System-on-Chip (SoC) designs while promoting security-aware verification and tool development. This paper presents a systematic study of SoC security verification through open-box hardware hacking competitions, focusing on practical vulnerability analysis strategies, observed findings, and lessons for security-aware verification. We present a multi-strategy vulnerability analysis methodology, combining simulation-based verification, formal verification, lint analysis, Large Language Model (LLM)-assisted bug detection, and coverage-guided hybrid fuzzing. Representative vulnerability findings are analyzed to illustrate how different techniques expose complementary classes of security flaws, and we derive practical lessons for pre-silicon security verification. Finally, we discuss how competition benchmarks can support the reproducible evaluation of emerging hardware security techniques and guide future security-aware EDA research.

### 1. 核心问题与整体含义（研究动机与背景）

- **背景**：传统系统安全假设底层硬件正确可信，防御重点集中于软件漏洞。然而，Meltdown、Spectre 以及电源/故障注入等攻击表明，硬件设计缺陷可完全瓦解软件层面的隔离机制。
- **核心问题**：硬件漏洞（如访问控制缺陷、特权检查不足、密钥管理不当、调试认证缺陷等）无法在流片后轻易修复，必须在流片前（pre-silicon）RTL 设计阶段发现。但传统 EDA 环境缺乏安全感知的验证流程——功能验证只验证设计是否符合架构规范，很少验证是否允许非预期的恶意行为。
- **研究切入**：硬件黑客竞赛（Hack@DAC、Hack@DATE、Hack@CHES 等）提供开放式（open-box）的 RTL SoC 设计供参与者分析，是检测未知漏洞、验证有效验证方法的理想平台。然而，现有研究多局限于特定方法或威胁模型，缺乏对大规模 SoC 系统分析的系统化指导。
- **研究意义**：本文旨在形式化系统性方法论，用于识别微妙的硅前漏洞、讨论缓解策略、总结实践教训，并将竞赛经验反馈到安全感知 EDA 研究，推动预硅验证的进步。

### 2. 方法论

论文提出了一种**多策略漏洞分析工作流**，核心思想是：
- **安全意图优先**：先明确受保护资产、信任边界、特权规则和预期安全行为，再判断测试失败或 RTL 代码是否为安全漏洞。
- **多维度互补验证**：不同验证方法从不同视角生成候选漏洞，再通过独立证据交叉验证，减少误报。

**关键技术细节与四阶段分析流程**：

1. **环境构建与基线建立**：搭建设计环境，运行可用的测试、形式验证和 lint 流程，建立基线。
2. **多策略候选漏洞生成**：每种策略独立生成漏洞候选。
3. **候选审查与去重**：人工审查排除工具错误、无效假设和重复发现。
4. **漏洞验证与报告**：使用自定义测试或形式化反例复现，映射到 CWE，记录安全影响和缓解建议。

**五项核心分析策略**：

| 策略 | 工具 | 核心目标 |
|------|------|----------|
| 仿真验证 | Synopsys VCS + DVSim | 运行回归/smoke/stress 测试，识别失败测试、意外输出、断言失败、超时与异常状态跳转 |
| 形式属性与信息流验证 | Synopsys VC Formal | 用 SVA 断言验证安全属性（FPV）；检测保密/完整性违规的信息流路径（FSV） |

**LLM 辅助分析的四个步骤**：
- 安全感知设计分解（重点分析含密钥、特权、生命周期状态、调试授权等安全资产的模块）；
- CWE 识别（按模块功能缩小候选弱点类别）；
- CWE 引导的 RTL 缺陷分析（针对特定模式检查）；
- 目标安全属性生成（LLM 生成 SVA 并用传统 EDA 工具验证语义）。

### 3. 实验设计

- **目标设计**：基于 **OpenTitan** SoC 设计（开源根信任硅芯片），使用 2024/2025 Hack@DAC 和 2025 Hack@CHES 竞赛提供的**明知有漏洞的版本**，包含 RTL 源码、DV 环境、安全属性、仿真测试和商用 EDA 工具。
- **基准场景**：针对 AES、HMAC、CSRNG、LC CTRL、OTBN、KMAC、UART、SPI TPM、Entropy Source、Power Manager 等多个 IP 进行系统的安全分析。
- **对比方法**：论文的主要对比逻辑是五种验证方法（仿真、形式验证、lint、LLM 辅助、模糊测试）在**不同漏洞类别上展现的互补能力**，并在文中以代表性漏洞案例（9 个表格）展示了每种方法发现的漏洞类型。同时对比分析了开放式与封闭式竞赛模型、不同硬件安全竞赛（CSAW LLC、HeLLO: CTF、WhibOx、CSAW AI 硬件挑战）的目标差异。

**发现的主要漏洞类别（7 类）**：
- 数据净化失败（Data Sanitization Failures）
- 敏感数据暴露（Sensitive Data Exposure）
- 访问控制违规（Access-Control Violations）
- FSM/控制流问题（FSM/Control-Flow Issues）
- 错误处理不当（Incorrect Error Handling）
- 完整性弱点（Integrity Weaknesses）
- 数据路径/信号控制错误（Data-Path/Signal-Control Errors）

**代表性漏洞示例**：
- AES：密钥/敏感状态未被安全清除；`SecAllowForcingMasks` 参数硬编码为 1，使掩码保护失效；密钥共享通过寄存器读路径泄漏；
- HMAC：密钥寄存器的 `reg2hw.key` 被赋值到 `reg_rdata_next`（密钥可被软件读取）；`wipe_secret_we` 依赖错误的 `reg_error` 信号；
- UART：接收端奇偶校验错误信号不依赖 `parity_enable`；`lsio_trigger_o` 在无效 FIFO 条件下被无条件触发；
- LC CTRL：DFT/调试功能在生产生命周期状态（LcStProd）被错误启用。

### 6. 主要结论与发现

1. **安全意图是漏洞识别的关键**：功能失败不等于安全漏洞，必须结合受保护资产、信任边界和特权规则来判定。
2. **不同验证方法具有互补性**：仿真利于复现可执行攻击序列；形式验证利于时序属性和难触达状态；静态分析可大规模结构筛查；信息流分析直接检测保密/完整性违规。
3. **现有验证基础设施需要安全感知指导**：功能覆盖不覆盖对抗性行为，安全定向的测试激励与覆盖率指标是必要的。
4. **自动化结果必须独立验证**：lint 警告、LLM 假设、断言失败、模糊测试异常都只是"候选"漏洞，必须追溯到 RTL 根因并用仿真/形式反例/信息流路径复现。
5. **跨层分析对 SoC 级漏洞必不可少**：很多漏洞的激活依赖寄存器事务、固件操作、特权状态，孤立分析模块难以发现。
6. **工具自动化与并行化显著提升覆盖率**：HJSON 编排的自动化执行以及多方法智能体 LLM 工作流比单一技术顺序分析更高效。
7. **竞赛基准对硬件安全研究具有长期价值**：可复用基准支持信息流追踪、CWE 引导分析、LLM 辅助检测等多种方法的可复现评估。

### 7. 优点

- **综合性强**：在统一框架下融合传统验证（仿真、形式化、lint）与新兴 AI 技术（LLM 辅助分析、混合模糊测试），展示了互补策略的系统集成方式。
- **实践导向**：以真实竞赛环境中的 OpenTitan SoC 为对象，发现的实际 CWE 映射漏洞具有较高的真实性和说服力。
- **交叉验证机制设计良好**：强调候选漏洞必须经多方法独立验证，降低误报风险。
- **自定义 exploit 演示完整**：以 UART 和 HMAC 为例，展示了从漏洞描述 → RTL/验证组件定位 → LLM 生成修改 → UVM 仿真 → 功能检查确认的完整闭环，可复现性较强。
- **分类体系清晰**：将 7 类安全缺陷与对应验证方法的关系进行了系统梳理，对安全验证方法选型有实际指导意义。
- **对 EDA 社区有启发**：讨论了安全覆盖度量、跨层级验证、安全 EDA 工具缺口等前瞻性方向。

### 8. 不足与局限

- **量化评估缺失**：未提供各方法在检测率、误报率、召回率、运行时间等维度的量化数据，难以客观比较不同方法的优劣。

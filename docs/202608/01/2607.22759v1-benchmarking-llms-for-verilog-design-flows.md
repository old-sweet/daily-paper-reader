## 摘要
大语言模型（LLM）在代码生成方面显示出潜力，但它们生成正确、可综合的硬件描述语言（HDL）代码的能力仍有待适当基准测试。现有评估主要依赖pass@k指标，缺乏完整的端到端工具链验证。本文提出了一个可复现的基准测试平台，在50个精选任务（包括组合、时序、有限状态机（FSM）和混合设计）上评估开源LLM的Verilog RTL生成能力。该流水线包括约束提示、后处理以及语义感知的迭代优化，并结合波形分析、形式等价性验证和基于抽象语法树（AST）的修复，通过Verilator编译和Icarus Verilog仿真对生成的代码进行验证。在12个基准测试和总共1,610次运行中，评估了三种不同规模的模型（Llama-3-8B、StarCoder2-7B和TinyLlama-1.1B），该流水线将三种开源模型的语法有效性从0%提高到平均70.43%，仿真通过率提高到51.8%。最值得注意的是，TinyLlama（1.1B参数）取得了最高的单项语法有效性80.0%，且功能正确性与8B模型相当。该平台和数据集是开源的，使生成式AI在硬件设计工作流中的可复现评估成为可能。

## Abstract
Large language models (LLMs) show promise in code generation, but their capabilities to produce correct, synthesizable hardware description language (HDL) code still remain to be properly benchmarked. Existing evaluations are primarily relying on pass@k metrics and lack proper end-to-end toolchain validation. This paper presents a reproducible benchmarking platform that evaluates open-source LLMs on Verilog RTL generation across 50 curated tasks consisting of combinational, sequential, finite state machine (FSM), and mixed designs. The pipeline consisting of constrained prompting, post-processing, and semantic-aware iterative refinement with waveform analysis, formal equivalence verification, and Abstract Syntax Tree (AST)-based repair validates the generated code via Verilator compilation and Icarus Verilog simulation. Across the 12 benchmarks and the 1,610 total runs evaluating three models of different sizes (Llama-3-8B, StarCoder2-7B, and TinyLlama-1.1B), the pipeline improved syntax validity from 0% to a 70.43% average and simulation pass rate to 51.8% across three open-source models. Most notably TinyLlama (1.1B parameters) achieved the highest individual syntax validity at 80.0%, with functional correctness comparable to the 8B model. The platform and dataset are open-source, enabling reproducible evaluation of generative AI for hardware design workflows.

### 1. 核心问题与整体含义（研究动机与背景）
- **背景**：SoC 复杂度持续增长，但精通 RTL 验证的工程师严重短缺。LLM 在通用代码生成上表现出潜力，但能否生成**正确、可综合**的 HDL 代码尚未得到充分验证。
- **核心问题**：现有评估（如 VeriGen 等）多依赖软件领域的 **pass@k** 指标，仅检查"k 个样本中是否有一个能编译"，无法回答实际问题：生成的 Verilog 能否通过 lint 检查？能否通过自检验证 testbench 的仿真？能否被综合为逻辑门？
- **本文定位**：针对该空白，构建了一个**可复现的端到端基准平台**，检验 LLM 生成的 Verilog 是否真正"能构建"——涵盖编译（Verilator）、仿真（Icarus Verilog）和综合（Yosys）全流程，并对失败代码进行迭代修复。

### 2. 方法论：核心思想、关键技术细节与算法流程
- **总体现念**：将 LLM 生成的 RTL 视为**草稿**而非交付物，通过"约束生成 → 后处理 → 工具链验证 → 语义感知修复"的**受控生成流水线（Guarded Generation Pipeline）**来提升正确性。
- **四步工作流（Tutorial）**：
  1. **先生成前指定（Specify before generating）**：预先收集模块名、完整端口列表（信号名、方向、位宽）以及结构约束（时钟域、复位极性、FSM 拓扑），存放于 `tasks.json`。
  2. **约束注入与后处理（Inject constraints & post-process）**：将精确模块签名、显式 Verilog-2001 语法规则、模块示例嵌入提示词；以温度 0.0 运行生成后，执行后处理（`post_process_verilog()`）：包括模块名纠正、端口强制、`logic` → `wire/reg` 转换、BSV 伪影移除、时序归一化、FSM/混合模板脚手架等六步转换。
  3. **真实工具验证（Validate with real tools）**：Verilator lint-only 模式捕获语法错误/端口不匹配 → 配对自检 testbench 运行 Icarus Verilog 仿真（30 秒超时）→ Yosys 综合作为最终门级确认。
  4. **定向反馈修复（Repair with targeted feedback）**：将编译器错误和仿真不匹配压缩为 ≤500 字符的修复提示，最多迭代 5 次。
- **五阶段演进与消融设计**：
  - **Phase 1 基线**：无约束的 few-shot 提示，语法有效性为 0%。
  - **Phase 2 约束提示**：注入精确模块名、端口规格、语法约束。
  - **Phase 3 后处理**：六重正则/AST 转换规则。
  - **Phase 4 语义感知迭代优化**：新增 `FeedbackGenerator`（≤500字符错误反馈）、`WaveformAnalyzer`（逐周期比较 VCD 信号）、`FormalVerifier`（Yosys `equiv_make`/`equiv_simple` 形式等价验证）、`ASTRepair`（基于 pyverilog 解析结构修复）、`ConfidenceTracker`（利用 Shannon 熵决定是否跳过昂贵语义工具）。任务分为三层：Tier 0（简单组合，单次迭代，无语义工具）、Tier 1（标准时序，最多 5 次迭代 + 波形 + AST）、Tier 2（复杂 FSM/混合，最多 5 次迭代 + 完整语义栈含形式验证）。
  - **Phase 5 FSM 增强**：在提示中嵌入显式状态转移表（替代自然语言描述）、提供对比性错误/正确 FSM 示例、严格模式（禁用熵门控）、针对缺失 default 语句/未闭合 begin-end/复位逻辑错误的微修复；迭代上限增至 6，改进阈值从 0.1 降至 0.05。

### 3. 实验设计：数据集、基准与对比
- **数据集**：50 个任务，分为：23 组合逻辑（门、加法器、多路选择器、译码器等）、14 时序逻辑（触发器、计数器、移位寄存器）、8 个 FSM（序列检测器、交通灯控制器、旋转门控制器等）、5 个混合设计（优先级编码器、ALU 等）。每个任务配备：可综合的 Verilog-2001 参考实现、确定性激励的自检 testbench（统计通过/失败用例数）、显式 I/O 元数据；同一任务以 `_001/_002/_003` 后缀改变自然语言措辞以隔离措辞效应。
- **评估模型**：
  - **Llama-3-8B-Instruct**（通用指令微调，Ollama 部署）
  - **StarCoder2-7B**（代码语料训练，HuggingFace Transformers）
  - **TinyLlama-1.1B**（比 Llama-3-8B 小 7 倍，Ollama 部署）
- **实验流程**：全部模型以温度 0.0、512 token 上限运行；每任务每模型重复 3 次；结果以均值 ± 标准差报告。
- **工具链**：Icarus Verilog 12.0、Verilator 5.038、Yosys 0.58（Homebrew 安装于 macOS Apple Silicon）；提供 Docker 镜像验证跨平台可复现性；所有运行配置在 `instruction.json` 单文件声明。
- **对比基线**：与 VeriGen、VerilogEval、AutoVCoder、AutoBench、HaVen 沿 9 个评估维度（任务类型、模型数、指标类型、仿真、形式验证、修复、综合/PPA、开源）进行对比——本文是唯一同时覆盖仿真 + 形式验证 + 修复 + 综合 + 开源的平台。

### 4. 资源与算力
- **明文说明**：论文**未明确披露 GPU 型号、数量或训练时长**；所有推理在 **macOS（Apple Silicon）** 上本地完成，使用 Ollama 和 HuggingFace Transformers 进行部署。
- 作者在威胁有效性部分指出：Apple Silicon 推理存在**硬件级非确定性**，导致温度 0.0 下仍有运行间方差。
- 模型均为**预训练开源模型，未经微调**；不涉及训练阶段的计算开销。

### 5. 实验数量与充分性
- **总运行量**：12 个基准阶段（Benchmark 1–12），共 **1,610 次运行**；Benchmark 12 为 50 任务 × 3 模型 × 3 重复 = 450 次运行。
- **消融实验（12 个基准递进）**：
  - BM1 基线 few-shot → BM2 约束提示 → BM3 后处理 → BM4 计时插桩 → BM5 加第三模型 → BM6 时序归一化 → BM7 扩展至 20 任务（引入 FSM/混合）→ BM8 FSM 模板脚手架 → BM9 迭代优化 → BM10 扩展至 50 任务 → BM11 仅 Llama-3-8B 复现性检查 + 生成时间优化 → BM12 Phase 5 完整版。
- **语义验证**：波形级逐周期对比、Yosys 形式等价验证、AST 级结构修复、Yosys 综合（统计细胞数）。
- **充分性评价**：
  - **充分**：12 阶段消融覆盖每个组件的边际贡献；每任务 3 次重复给出方差；合成与形式验证补充了仿真盲区；跨 3 种不同规模/训练范式的模型对比。
  - **客观性**：形式等价验证与参考 testbench 属于确定性验证而非模型自评；开源发布支持独立复现。
  - **不充分之处**：仅 50 个单模块任务，规模有限；3 个模型难以代表更广泛的最先进模型；未做多次随机种子验证（仅 3 次重复）；无跨操作系统/工具链版本的测试（仅 Docker 内 mini-benchmark 5 任务 × 3 模型）。

### 6. 主要结论与发现
- **总体效果**：语法有效性从 **0% 提升至平均 70.43%**；仿真通过率达到 **51.8%**（Benchmark 12 的三种模型均值）。
- **关键发现 1——提示精度 > 模型规模**：约束提示 + 后处理带来的增益（0%→60%）大于任何模型间差异；无约束时所有模型完全无法生成可编译代码。
- **关键发现 2——FSM 仍然困难**：FSM 和混合设计在全部 12 个基准中始终最差；FSM 综合率仅 43.1%；即使经过 Phase 5 增强，1-8B 开源模型仍无法可靠处理复杂状态机。
- **关键发现 3——小模型反超**：**TinyLlama-1.1B 语法有效性最高（80.0% ± 3.5%），仿真通过率（60.7% ± 5.0%）接近 Llama-3-8B（59.3% ± 1.2%）**；表明约束化 RTL 生成中，工作流设计可能比模型规模更重要。
- **StarCoder2-7B 意外落后**：尽管经过代码语料训练，Verilog 在其训练数据中占比很小，其语法有效性仅 59.3%，且合成输出细胞数最高（12.1 vs 5.6/3.5），表明生成结构性冗长而非紧凑 RTL。
- **综合结果**：450 次运行中 66.7% 可综合；时序设计综合率最高（85.7%，平均 5.0 个细胞）；FSM（43.1%）和混合设计（48.9%）综合率最低。
- **四种典型失败模式**：①状态转移坍塌（复制而非反转转移，如旋转门控制器输出时序错误）；②Moore/Mealy 混淆（输出逻辑组合化，导致早一个时钟周期断言）；③缺少 default 分支阻断综合（仿真可过、综合必挂）；④混合设计丢弃寄存输出级（仅实现组合路径）。

### 7. 优点
- **端到端工具链验证**：超越了纯 pass@k 评估，将编译、仿真、综合、形式等价验证全部纳入评估闭环，回答"能否真正构建"这一工程核心问题。
- **深度消融设计**：12 个递增基准清楚分解每个组件（约束提示、后处理、模板脚手架、迭代优化、FSM 增强）的边际贡献，方法论清晰可复制。
- **语义感知修复组合策略**：波形分析 + 形式验证 + AST 修复 + 置信度熵门控的多层修复机制，按任务难度分层分配计算资源（Tier 0/1/2），兼顾效率与效果。
- **开放可复现**：平台、数据集、Docker 镜像、`instruction.json` 全量配置开源；3 次重复 + σ 报告体现严谨性。
- **失败分析细致**：从结构、时序、FSM、混合四层归纳失败分类学，并给出具体代码示例（如旋转门控制器）和修复对应关系，对实践极具指导价值。
- **发现具有普适意义**：小模型在约束工作流中可比肩甚至超越大模型、提示工程增益大于模型升级等结论，对 EDA 行业的实际部署策略有直接参考价值。

### 8. 不足与局限
- **数据集覆盖面窄**：仅限单模块、完全指定、确定性可测试设计；**缺乏层次化 RTL、总线协议（如 AXI/APB）、多时钟域设计**——这些恰恰是生产级芯片设计中最常见的复杂度来源。
- **无可综合后量化指标**：未测量面积（area）、时序（timing）、功耗（power）等 PPA 指标；可综合性只是硬件可用性的必要而非充分条件，LLM 代码能否满足真实工艺角下的时序约束仍悬而未决。
- **FSM 修复效果有限**：作者坦承仿真失配反馈对 FSM 状态转移错误的修复信号"过于粗糙"，即使 5-6 次迭代也无法根本改善最困难任务的逻辑正确性。
- **参考 testbench 定义正确性带来高估风险**：某些任务的测试激励覆盖有限，可能产生过度报告的通过率；形式验证虽部分缓解，但并非所有任务都启用（Phase 4 默认关闭，仅在 Tier 2 开启）。
- **模型覆盖范围有限**：仅 3 个 1-8B 规模的开源模型，未覆盖更大规模的商用模型（GPT-4/Claude）或专门微调的 Verilog 模型。
- **硬件非确定性**：Apple Silicon 推理在温度 0.0 下仍存在运行间方差，且未做跨操作系统/工具链版本的充分验证，尽管 Docker 镜像在一定程度上缓解了该问题。
- **规模效应不明**：作者自述 50 个任务的选量部分出于算力考量（450 次运行/基准），更大规模任务集的可扩展性未得验证。

## 摘要
本文介绍了CHARGE，一个使用CWE和大语言模型（LLM）为未验证RTL模块自动生成安全属性的框架。其标志性是一个推理过程，利用CWE条目的层次性质，在识别未验证RTL模块中的安全关键资产时提高准确性。因此，该方法可以推断预期的安全行为，并根据已识别的资产和CWE语义生成属性，避免了受信任设计规范的需求，并减少了手动工程工作。我们使用OpenAI的GPT-4.1在Hack@DAC18、19和21开源SoC设计上评估了该框架。CHARGE在这些设计中检测到42个已知错误中的27个。对于Hack@DAC21 OpenPiton SoC，89%的生成SVA在Cadence JasperGold FPV中运行，92.2%是非空的。我们与这些设计的开源手动编写属性集进行比较，发现CHARGE正确地为三个手动编写属性错误的错误编写了属性。此外，CHARGE生成的属性在Hack@DAC21 OpenPiton SoC中发现了一个以前未识别的新错误。

## Abstract
This paper presents CHARGE, an automated framework for generating security properties for unverified RTL modules using CWEs and large language models (LLMs). The hallmark is a reasoning process that leverages the hierarchical nature of CWE entries to improve accuracy when identifying security-critical assets in unverified RTL modules. As a result, the approach can infer expected security behaviors and generate properties from identified assets and CWE semantics, avoiding the need for trusted design specifications and reducing manual engineering effort. We evaluate the framework on the Hack@DAC18, 19, and 21 open source SoC designs using OpenAI's GPT-4.1. CHARGE detects 27 of 42 known bugs in these designs. For Hack@DAC21 OpenPiton SoC, 89% of the generated SVAs run in Cadence JasperGold FPV, and 92.2% are non-vacuous. We compare to an open-source, manually written set of properties for these designs and find that CHARGE correctly writes properties for three bugs in which the manually written properties were incorrect. In addition, CHARGE-generated properties identify a new bug in the Hack@DAC21 OpenPiton SoC that was not previously identified.

## 1. 核心问题与研究动机

- 硬件安全漏洞可能导致整个系统被攻破，因此**在设计生命周期早期进行安全验证**至关重要。
- 断言（Assertion）是硬件验证的核心手段，例如模型检验（Model Checking）可证明设计不会违反断言，符号执行（Symbolic Execution）和模糊测试（Fuzzing）则可在大型设计中寻找断言违例。
- 安全断言的有效性完全取决于断言自身的质量，而**编写一套全面、正确的安全断言是一项极具挑战且耗时耗力的任务**。
- 现有的自动方法（如行为挖掘、属性翻译、模板生成）各有局限；新近兴起的**大语言模型（LLM）断言生成**面临两大核心挑战：
  1. **需要非常详细的指导**才能生成有意义且准确的断言；
  2. **设计本身可能含 bug**，不能假设其无错、不能将其作为干净的规范输入给 LLM。
- 对于**功能验证**，可通过向 LLM 提供设计规格（信号名、时序、预期行为）来应对；但对于**安全验证**，不存在设计特定的安全规范。CWE（Common Weakness Enumeration）数据库提供了高层次安全目标，但它是通用性的、非设计特定的，**将高层次目标映射到具体设计的信号、时序和行为是核心难题**。

## 2. 方法论

### 2.1 核心思想

- 提出 **CHARGE（CWE Hierarchy AsseRtion Generation Engine）**，利用 CWE 数据库的**层次结构**作为“规范替代品”，引导 LLM 直接从未验证 RTL 生成安全断言。
- 核心洞察：**CWE 的父节点比子节点更抽象**，即使 RTL 中缺失关键行为（即 bug 所在），从高抽象层父节点出发也能识别出相关资产，从而避免被缺陷 RTL 误导。

### 2.2 CWE 结构化表示——3-tuple

- 每个 CWE 描述被分解为结构化三元组：**⟨target, action, condition⟩**
  - **target**：被保护的安全资产（如密钥、数据、内存区域）；
  - **action**：对目标执行的操作（如读、写、清零）；
  - **condition**：允许/禁止该动作的约束条件（如特权级、锁定位、状态标志）。
- 示例（CWE-226：资源重用前未移除敏感信息）：
  - ⟨敏感资源，净化/清零，重用/释放条件⟩
  - 对应模板 SVA（Listing 1）在复位触发事件后检验资源敏感数据是否为 0。

### 2.3 CWE 覆盖范围的分类

- 聚焦于 **CWE-1194（Hardware Design view）** 中 MITRE 标记为“Mappable”的硬件 CWE，共 110 个。
- 分类为两类：
  - **Convertible（37个）**：安全策略可完全由单个 3-tuple 表示，并映射到断言模板；
  - **Partially Convertible（27个）**：仅部分安全意图可由此表示，需要额外的行为推理（利用 LLM 的创造性）。
- 还排除了 14 个物理环境类、12 个侧信道/信息流类、9 个软件/算法/ISA/系统级以及 11 个需要协议信息的 CWE（如表 1 所示）。

### 2.4 CWE 层次树构建

- 以 **CWE-1000（Research Concepts）** 为根，包含 10 个 Pillar 子树。
- 从每个可映射 CWE 出发，沿 "Child Of" 关系向上追溯至 pillar，构建树结构（仅保留 Parent–Child 关系，排除 CanPrecede/CanFollow）。
- 每个节点额外存储 3-tuple 字段“asset identification”，用于资产识别提示。
- 关键假设：**子 CWE 是父 CWE 的细化**，因此新增 CWE 可通过继承祖先的 3-tuple 并特化来纳入框架（图 1 用假想的 CWE-1999 演示）。

### 2.5 CHARGE 三步工作流（图 2）

**Step 1：LLM 支持的资产识别（最关键步骤）**
- 输入目标 CWE ID 和 RTL，从 CWE 树中检索从根到目标的层次路径。
- 将该路径和 CWE 层次 JSON 并入提示词，让 LLM 沿路径逐步处理每个 CWE 节点的 3-tuple 查询，识别各节点对应的资产。
- 输出 JSON 文件，将目标 CWE 及其父节点识别的资产作为“primary assets”，祖先节点资产作为“relevant assets”。
- 若 LLM 无法为目标 CWE 识别任何资产，则报告“inapplicable CWE”。
- 层次推理的价值：对于 CWE-226 目标但 RTL 中缺失 `msg_out` 清零行为的情况，由于 `msg_out` 在祖先 CWE-664 下被识别为相关资产，缺陷仍能被捕获。

**Step 2：LLM 支持的安全行为挖掘**
- 输入：Step 1 的资产（primary targets、primary conditions、relevant assets）+ RTL + 目标 CWE 描述 + 手工设计的策略问题。
- 策略问题针对每个 CWE 编写一次并复用，例如 CWE-226 的问题是“给定资产应在什么条件下被清零/净化？”。
- 输出：自然语言形式的预期安全行为列表（存储为 .txt），例如“复位开启时 msg_out 应被清除”。
- 明确要求 LLM 仅将 RTL 作为上下文参考，避免将缺陷行为错误地当作预期行为。

**Step 3：LLM 支持的 SVA 生成**
- 输入：Step 2 行为列表 + Step 1 资产 + 目标 CWE + RTL + 手工设计的 SVA 模板（每 CWE 一个，复用）。
- LLM 被要求基于预期行为填充模板，**只能使用 RTL 中真实信号**，禁止发明信号或使用 JasperGold 不支持的语法（如 for 循环）。
- 输出 .sv 文件，并为每个 SVA 生成 cover property 以检查空性（vacuous truth）。

## 6. 主要结论与发现

1. **端到端性能**：CHARGE 对 42 个已知 bug 中 **34 个识别出有用资产、29 个生成有意义行为、27 个生成可检测 bug 的断言**。
2. **基线提升明显**：在 Hack@DAC 2021 上，bug 检测从 Baseline 0 的 1/14（GPT-4.1）提升到 CHARGE 的 11/14；三种 LLM 均一致达到 11/14。
3. **可编译性与非空性**：Hack@DAC 2021 生成的 SVA 中 89% 可在 JasperGold 中直接运行，92.2% 非空（non-vacuous）。
4. **层次+3元组的贡献**：资产识别准确率（GPT-4.1）从无层次无 3 元组的 45.1% 提升到完整配置的 73.2%；三种 LLM 都显示一致提升趋势。
5. **发现人工属性错误**：3 处 Verification Benchmarks 手动属性不正确（操作符误用、地址范围错误），CHARGE 生成正确属性。
6. **发现新未知 bug**：在 Hack@DAC 2021 OpenPiton 的 aes0_wrapper 中发现未记录的复位后密钥残留问题。
7. **失败模式分析**：15 个未检测 bug 集中于 7 个 CWE（共享 4 个祖先），说明 LLM 对特定 CWE 类型敏感性差异显著（与 LASHED [2] 发现一致）；**RTL 模块长度是重要因素**（成功模块平均 355 行 vs 失败模块平均 872 行）。

## 7. 优点与亮点

- **无需设计规格**：利用 CWE 作为安全规范的代理，直接从可能含 bug 的 RTL 生成属性，突破了安全验证无规格可依的瓶颈。
- **利用 CWE 层次结构**：通过沿层次路径逐步识别资产，缓解了因 RTL 缺陷（如缺失清零行为）导致的关键资产无法识别问题——这是框架最核心的方法论创新。
- **系统化结构化分解**：3-tuple（目标/动作/条件）将自然语言 CWE 描述转化为可操作的、可复用的结构化格式，配合每 CWE 手工模板（策略问题、SVA 模板）实现跨模块复用，减少工程开销。
- **可扩展性**：新增 CWE 可通过继承祖先 3-tuple 并特化融入，保持向后兼容，随 CWE 数据库演化自然扩展。
- **跨 LLM 泛化能力**：在 GPT-4.1、Gemini 2.5 Pro、Claude Sonnet 4.6 上均一致地将 bug 检测提升到 11/14，证明收益来自方法论而非特定模型。
- **全面消融验证**：通过 Baseline 0（有无框架对比）和 Baseline 1（层次和 3-tuple 的逐项消融）清晰量化各组件贡献。
- **可复现性**：框架完全自动化、代码开源（GitHub 提供），中间产物逐级传递至最终 SVA。
- **应用性**：生成标准 SVA，与各类 SVA 兼容验证工具可用；可移植性讨论（仅需修改最终提示阶段适配新工具）。

## 8. 不足与局限

### 8.1 实验覆盖局限

- **仅覆盖 Hack@DAC 系列基准**：端到端评估局限于 Verification Benchmarks 仓库中具有 bug 和参考属性的 Hack@DAC 18/19/21 案例，支持的全部硬件 CWE 并未在基准中充分体现。
- **CWE 覆盖不均衡**：多数未检测 bug 集中于少数几个 CWE（如 CWE-1220、CWE-1281、CWE-1245），对部分 CWE 类型（如 FSM 类和稍复杂的长模块）检测能力有限。
- **手动排除案例**：4 个“无违例”属性和 2 个特殊 bug 被排除，可能引入选择偏差。
- **RTL 规模限制**：长模块（>800 行）中 11/15 的 bug 未检测出，框架对大型模块的有效性仍待验证。

### 8.2 技术局限与失败模式

- **资产/行为缺失（Type 1 失败）**——4 个根因：
  1. CWE 与 bug 不匹配（仓库中存在此问题）；
  2. RTL 中完全缺乏关键资产的证据；
  3. 大模块和复杂行为致 LLM 能力不足；
  4. 期望行为不在 LLM 训练数据中，无法建立资产

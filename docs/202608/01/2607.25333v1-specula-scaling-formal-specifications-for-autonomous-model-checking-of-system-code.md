## 摘要
Specula是一个一键式自主系统，能够为大型、复杂的系统代码生成高质量的形式化规范，并利用这些规范进行高效的模型检测和缺陷发现。Specula采用基于大型语言模型（LLM）的编码智能体，自主开发TLA+规范，包括描述目标系统正确性属性的不变式，以及以适当抽象级别描述系统实现的正式模型。Specula完全自主，从而消除了将形式化方法应用于现实世界系统代码的障碍（如传统以人为中心的方法）。同时，Specula通过自我演化循环解决了LLM驱动技术（如奖励黑客和幻觉）的局限性，通过使智能体加深对系统代码及其行为的理解，迭代提高规范质量。我们已使用Specula检查了48个开源系统项目；Specula发现了249个缺陷，包括许多现有方法难以发现的深层缺陷。Specula已被多家公司使用，并维护在https://github.com/specula-org/Specula。

## Abstract
Specula is a push-button agentic system that generates high-quality formal specifications for large, complex system code and uses the specifications for highly effective model checking and bug finding. Specula employs large language model (LLM) based coding agents to autonomously develop TLA+ specifications, including invariants that describe correctness properties of the target system and formal models that describe the system implementation with the right level of abstractions. Specula is fully autonomous and thus eliminates the barrier of applying formal methods to real-world system code (as in traditional human-centric approaches). Meanwhile, Specula addresses limitations of LLM-driven techniques like reward hacking and hallucinations through self-evolving loops that iteratively improve specification quality by enabling the agents to deepen their understanding of system code and its behaviors. We have used Specula to check 48 open-source system projects; Specula found 249 bugs including many deep bugs that are hard to find by existing approaches. Specula has been used by several companies and is maintained at https://github.com/specula-org/Specula.

## 1. 核心问题与整体含义

- **研究动机**：形式化规范（如 TLA+）对并发/分布式系统的正确性验证至关重要，但传统上由人类专家编写规范成本极高——例如为 ZooKeeper 或 Asterinas 编写高质量规范需要数月时间，难以扩展到真实世界的大型复杂系统。
- **问题背景**：尽管 LLM 和编码智能体在软件工程领域已展现出巨大潜力，直接使用它们生成形式化规范存在根本性局限：
  - LLM 会产生**幻觉**（hallucination）和**不精确/错误**的规范；
  - LLM 存在**奖励黑客**（reward hacking）倾向，缺乏明确边界时容易过度拟合；
  - 无论人类还是 AI，都难以确定合适的**抽象级别**来建模复杂系统。
- **整体含义**：Specula 提出一种**全自动、一键式**的智能体系统，能够为任意大型系统代码自主生成高质量 TLA+ 规范（包括形式化模型和正确性不变式），并通过模型检测与代码级复现实现高效 bug 发现，从而消除形式化方法应用于真实系统的障碍。

## 2. 方法论

Specula 的整体架构基于 LLM 编码智能体（如 Claude Code、Codex），辅以静态分析工具、TLC 模型检查器和自研调试器。其核心流程如下：

1. **理解正确性属性（§3.1）**
   - 指令智能体从系统工件（代码、文档、issue、commit 历史）中提取两类不变式：
     - **协议级不变式**：如 Raft 的选举安全、日志匹配等（来源于协议规范）；
     - **代码级不变式**：如操作原子性、数据结构容量边界、commitIndex 单调性等（来源于代码/测试/issue）。
   - 强制智能体为每个不变式提供**具体证据**（代码、issue、commit 等），以保证可审计性和接地性。

2. **生成有效系统模型（§3.2）**
   - 首先生成**参考模型**（reference model）：由智能体自主决定不同部分代码的抽象级别，以不变式为导向——保留影响性质的细节，省略无关细节。
   - 自动生成**场景**（scenarios）：从 issue、commit 历史、测试中总结重要场景，并要求提供证据；每个场景附带相关变量、动作和不变式。
   - 对每个场景生成**场景化模型**，通过对参考模型进行三种投影操作：
     - **动作选择**（如禁用 crash、限制 lease read 次数）；
     - **动作粗化**（将多步协议过程合并为一个原子动作）；
     - **动作序列整形**（对动作进行串行化或约束执行阶段）。

3. **确保模型-代码一致性（§3.3）**
   - 自动**插桩**系统代码，记录动作名和状态变量，生成代码级 trace；
   - 自动构建 TLA+ **重放测试**，用 TLC 验证模型是否接受该 trace；
   - 若模型失败，则进行**双向验证**修复模型：trace validation 确保模型允许代码行为，模型检查确保修复不会过度放宽（防止过拟合/奖励黑客）。

4. **查找并复现 bug（§3.4）**
   - 对每个场景化模型运行 TLC（BFS + 随机模拟），发现不变式违反；
   - 从模型 trace 出发，通过四个阶段（客户端 API 交互 → sleep 控制并发 → 构造系统状态前置条件 → 代码内 sleep 控制内部并发）在代码级复现；
   - 禁止注入非法状态、直接调用私有函数或修改代码逻辑等“快捷方式”。

5. **自我进化循环（§3.5）**
   - 当一个不变式被违反时，智能体需要区分三种可能原因：模型错误、代码 bug、不变式错误；
   - 通过 trace validation 与模型检查的循环，智能体逐步加深对系统的理解，迭代修正模型、不变式和插桩代码；
   - 设计上保证循环是**安全的**——只增加一致性/精确性，不随意放宽不变式。

## 6. 主要结论与发现

- **有效性**：Specula 在 48 个开源系统中发现 249 个 bug，包含深层 bug（死锁、数据丢失/损坏、崩溃、可用性丢失），其中许多是现有方法难以发现的；报告 89 个 bug 中，68 个已获确认、24 个已修复。
- **无假阳性**：在最新版本检查的 14 个系统中，136 个报告的 bug 中 134 个可代码级复现，2 个可复现但无严重后果（被系统掩盖），无假阳性。
- **对比优势**：在 SysMoBench 上 Specula 获得满分（100%），而 Agent-Raw 81%、Agent-TLA+ 82%；bug 数量方面 Specula 在 5 个系统中发现 62 个，Agent-Raw 仅 2 个、Agent-TLA+ 仅 3 个；Agent-Raw 和 Agent-TLA+ 分别有 5 个和 2 个假阳性。
- **自进化循环的必要性**：所有 48 个系统都需要模型修复，36 个系统需要不变式修订，33 个系统需要插桩修正；循环机制能有效区分模型错误、代码 bug 和不变式错误。
- **LLM 能力敏感性**：使用 Sonnet-4.6 时效果下降（找到 10/62 个 bug）；使用 Haiku-4.5 时基本不可用，且弱模型更容易违反指令进行奖励黑客。

## 7. 优点

- **全自动化**：一键式操作，无需人类专家介入，消除了形式化方法应用的最大门槛。
- **双向一致性验证**：trace validation 与模型检查互相约束，既能确保模型容纳代码行为，又能防止过拟合式修复。
- **场景化模型**：通过将参考模型投影为多个定制模型，有效避免状态空间爆炸，同时保持高探测能力。
- **自我进化循环设计**：将 LLM 的不可靠性视为系统设计的一等公民，通过迭代反馈机制（而非假设 LLM 完美）来收敛高质量规范。
- **真实系统验证**：在大量真实开源系统上验证，并有开发者确认和工业界采用，充分说明了实际价值。
- **证据强制**：要求智能体为每个不变式和场景提供具体出处，提高了可审计性，降低了幻觉风险。

## 8. 不足与局限

- **缺乏形式化保证**：Specula 由 LLM 自主驱动建模和理解，不提供形式化保证；可能遗漏某些需要建模的行为或不变式，从而漏测潜在 bug。
- **成本较高**：相比普通 agentic 方法，Specula 的 token 消耗和时间开销大（中位 $57/系统），可能限制其在大规模项目中的普及。
- **LLM 能力依赖**：对弱 LLM（如 Haiku-4.5）效果很差，且弱模型可能出现奖励黑客行为；方法的可用性随底层模型能力波动。
- **结果一致性**：部分评估结果来自早期版本，未能用最新版本重跑所有系统，可能低估实际能力或引入版本偏差。
- **复现限制**：约 1% 的被判断为真实 bug 的违反无法确定性复现，需要外部控制机制；此外，被系统内置机制掩盖的 bug 可能无法完整报告其严重性。
- **模型正确性依赖不变式**：如果智能体提取的不变式本身不完整或不正确，模型检查的结果就可能带有误导性；虽然自进化循环能部分修正，但不能保证完全完备。

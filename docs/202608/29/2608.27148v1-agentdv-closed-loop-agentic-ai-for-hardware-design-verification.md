## 摘要
寄存器传输级（RTL）验证消耗了现代片上系统（SoC）开发工作的大部分。然而，近期基于LLM的验证代码生成往往无法生成可运行、与设计一致且能产生覆盖率的测试平台。我们提出了AgentDV，一种用于自动化RTL验证环境生成的闭环智能体AI框架。AgentDV通过结合LLM引导的分析、测试平台构建、仿真、覆盖率度量和迭代细化，将单次LLM测试平台生成转变为基于工具的验证流水线。该框架引入了三个关键思想：1) 可运行性过滤，以拒绝无效的生成环境；2) 基于CSR的检查，以减少幻觉信号和错误的预期行为；以及3) 覆盖率引导的迭代，根据测量的验证差距重新生成测试。我们使用三个LLM在挑战性DUT和公开的OpenTitan外设及安全IP模块上评估了AgentDV。从我们的分析中，我们观察到直接的单次提示在基准测试上无法产生有效的、能产生覆盖率的验证环境。AgentDV在使用Claude Sonnet 4.6时，在四个DUT上实现了100%的通过率，在所有DUT上平均通过率为80.9%。类似地，Llama和Qwen模型的平均通过率分别为58.7%和60.6%。此外，对于所考虑的基准测试，Claude Sonnet 4.6、Llama和Qwen模型分别实现了平均74.5%、69.1%和64.9%的行覆盖率，以及88.4%、82.3%和76.7%的分支覆盖率。

## Abstract
Register-transfer level (RTL) verification consumes a major part of modern system-on-chip (SoC) development effort. Yet, recent LLM-based verification-code generation often fails to produce runnable, design-consistent, and coverage-producing testbenches. We present AgentDV, a closed-loop agentic AI framework for automated RTL verification environment generation. AgentDV transforms single-shot LLM testbench generation into a tool-grounded verification pipeline by combining LLM-guided analysis, testbench construction, simulation, coverage measurement, and iterative refinement. The framework introduces three key ideas: 1) runnability filtering to reject invalid generated environments, 2) CSR-grounded checking to reduce hallucinated signals and incorrect expected behavior, and 3) coverage-guided iteration to regenerate tests based on measured verification gaps. We evaluate AgentDV using three LLMs on challenge DUTs and public OpenTitan peripheral and security IP blocks. From our analysis, we observed that direct single-shot prompting fails to produce a valid coverage-producing environment on benchmarks. AgentDV achieves 100% pass rate on four DUTs and an average of 80.9% pass rate on all DUTs using Claude Sonnet 4.6. Similarly, an average of 58.7% and 60.6% pass rate is achieved for Llama and Qwen models, respectively. In addition, an average of 74.5%, 69.1%, and 64.9% of line coverage and 88.4%, 82.3%, and 76.7% of branch coverage for the benchmarks under consideration for Claude Sonnet 4.6, Llama, and Qwen models, respectively.

## 1. 核心问题与研究动机

RTL（寄存器传输级）功能验证是SoC开发中的主要瓶颈，消耗约50–60%的ASIC项目总时间。随着设计复杂度持续增长，验证工作高度依赖人工且流程繁琐，这促使研究者探索自动化验证工作流。近年LLM在HDL代码生成方面取得进展，但在**验证环境生成**方面仍面临关键挑战：

- **单次生成往往不可运行**：LLM直接生成的测试平台常引用无效信号、假设错误的寄存器行为，导致仿真快速失败。
- **检查逻辑不可信**：既有方法（如AutoBench、CorrectBench、PRO-V-R1）依赖LLM生成的参考模型来校验预期行为，但参考模型本身若错误，测试可能在检查逻辑本身有缺陷时仍然"通过"。
- **缺乏闭环反馈**：一次性生成无法利用仿真结果和覆盖率信息迭代优化测试套件。
- **领域偏移**：现有研究主要在学术RTL基准（VerilogEval、RTLLM）上评估，对实际IP级设计的验证自动化探索不足。

论文作者基于ISQED 2026智能体AI设计验证挑战赛的AutoVerifier任务设定，提出AgentDV框架，将自主验证视为**工具接地（tool-grounded）的闭环验证循环**，而非一次性代码生成任务。

## 2. 方法论：核心思想与技术细节

AgentDV的目标是将输入元组 I = (R, S, M)——分别代表RTL源码、自然语言规格说明、CSR寄存器映射——转化为可执行的验证包 O = (E, T, C, F)，其中E为验证环境、T为测试套件、C为覆盖率报告、F为验证发现（bug报告）。

### 2.1 核心思想（三个关键设计）

| 关键思想 | 作用 |
|---------|------|
| **可运行性过滤（Runnability Filtering）** | 在将生成的测试纳入测试套件之前，通过语法解析和单测仿真验证其可运行性，拒绝无效生成物 |
| **CSR接地检查（CSR-grounded Checking）** | 从CSR映射中确定性推导寄存器地址、复位值、字段编码和访问策略，利用pyUVM的寄存器抽象层（RAL）镜像机制校验预期行为，减少LLM幻觉 |
| **覆盖率引导迭代（Coverage-guided Iteration）** | 根据每次仿真产生的行/分支覆盖率反馈，针对未覆盖的RTL区域定向生成新测试 |

### 2.2 流水线架构（七阶段）

两个阶段组成：

**设置阶段（setup phase）：**
- **Analyze**：使用Verilator前端和OpenTitan reggen库解析RTL和CSR映射，提取端口列表、TL-UL总线接口、寄存器列表及字段访问策略。
- **Plan**：仅调用一次LLM，基于规格说明和寄存器列表生成带功能名、优先级和目标覆盖率bin的YAML验证计划。
- **Build**：完全模板化、机械式生成pyUVM RAL栈（uvm_reg_block子类、TL-UL适配器、环境布线）和模板化CSR测试套件（复位值检查、多模式读写、可写位walking-one测试）。所有测试调用 `reg.read(check_t.CHECK)`，由RAL库内镜像（而非测试代码）提供期望值。

**执行与收敛阶段（execution and closure phase）：**
- **Test**：针对验证计划中的每个条目（每DUT通常10–20个），LLM合成一个功能测试，扩展模板化CSR套件，然后通过cocotb + Verilator仿真运行。
- **Measure**：将仿真产生的覆盖率数据库解析为行、分支、翻转覆盖率，并标注未覆盖的RTL区域。
- **Iterate**：使用未覆盖区域注释和寄存器表提示LLM生成缺口定向测试，经可运行性检查后运行，仅在可运行且贡献覆盖率时纳入套件。终止条件：最多5轮迭代或连续2轮无覆盖率提升（`max_iterations=5, patience=2`）。
- **Report**：汇总每阶段输出为Markdown摘要、按失败分类的bug报告和结构化JSON代理日志。

### 2.3 可运行性检查（verify）

对每个LLM生成的测试执行两步验证：
1. **`ast.parse`** 语法解析
2. **单测试cocotb仿真**（Verilator下）

三种结果：
- **PASS** → 纳套件
- **Python崩溃** → 将异常文本作为错误反馈附带，重试一次；第二次崩溃则丢弃
- **RAL检查失败（断言错误）** → 保留为验证发现（表示硬件响应与镜像之间真实失配）

### 2.4 选择性检索（RAG）

本地文档库覆盖TileLink-UL协议、cocotb API、覆盖率API和pyUVM用法。仅当提示引用分析后DUT未定义的符号时才检索附加文档片段，使LLM调用聚焦且经济。

### 2.5 主要公式

**Pass Rate**（通过率）—— 通过可运行性检查的测试数中，在干净RTL上仿真无断言失败的测试占比：

```
PassRate = Npass / |Tverify| × 100
```

其中 Tverify ⊆ Tgen 为通过可运行性检查的子集，Npass 为其中无断言失败的测试数。

**Line/Branch Coverage**（行/分支覆盖率）—— 使用Verilator内置覆盖率支持：

```
LineCov = Nexecuted lines / Ntotal lines × 100
BranchCov = Ncovered branches / Ntotal branches × 100
```

## 6. 主要结论与发现

1. **直接单次提示彻底失效**：Claude在无AgentDV下，9个DUT全部无法产生有效的覆盖率产出环境（通过率0.0%），印证了闭环框架的必要性。

2. **AgentDV在Claude上表现最佳**：
   - 4个DUT达到100%通过率（nexus_uart、bastion_gpio、aegis_aes、opentitan_uart）
   - 所有DUT平均通过率80.9%（每DUT通过率见表：nexus_uart 100%、bastion_gpio 100%、warden_timer 91%、aegis_aes 100%、sentinel_hmac 36%、opentitan_uart 100%、opentitan_aes 55%、opentitan_hmac 55%、opentitan_rv_timer 91%）
   - 挑战基准平均行覆盖76.9%、分支覆盖95.7%；公共基准71.6%行覆盖、79.2%分支覆盖

3. **开放权重模型具备竞争力**：Llama平均通过率58.7%、Qwen 60.6%，两者覆盖率与Claude差距在25个百分点以内，无需API成本。

4. **通过率与覆盖率不成正比**：sentinel_hmac上Qwen通过率（73%）高于Claude（36%），但Claude覆盖率高得多（61.3%行/93.3%分支 vs 39.5%行/62.5%分支）。验证套件的"稳定运行"与"行为探索"是两种不同的属性。

5. **框架对控制型IP高度有效，对数据通路型IP存在边界**：
   - 外设型（GPIO、UART、Timer）达到近满覆盖：bastion_gpio 100%行/分支，warden_timer 97.7%行/100%分支
   - 密码型（AES、HMAC）行覆盖率停滞在约37–61%，生成测试主要覆盖寄存器解码和CSR控制路径，无法通过孤立CSR访问激活完整加密数据通路（需完整事务序列：密钥加载、明文加载、引擎启动、状态轮询、密文观测）

6. **闭环覆盖率迭代提供可测改进**：首次迭代收益最大（因LLM获得具体未覆盖区域信息），后续迭代收益递减，趋于覆盖率饱和。

## 7. 优点与亮点

- **全闭环设计**：将LLM生成从孤立的代码生成转变为"生成→执行→测量→反馈→再生成"的工程闭环，符合验证工作流的真实形态。
- **确定性设计事实与LLM推理的清晰分工**：寄存器/端口/总线接口等设计事实由确定性工具（Verilator/reggen）提取，LLM仅承担规划、推理和测试生成，最大限度减少幻觉。
- **RAL镜像机制的可信校验**：期望值来源于pyUVM库内的寄存器镜像，而非LLM生成的参考模型。若参考寄存器模型错误，LLM无法直接"作弊"通过断言。
- **三层防御**：语法解析（runnability）→ 单测仿真（可执行性）→ RAL断言（行为正确性），每一层过滤掉不同类别的无效物。
- **成本控制**：RAG仅按需触发（当提示引用未定义符号时），闭环最多5轮且连续两轮零收益即停，Claude单DUT仅需约150秒/0.11美元。
- **Token利用高效**：LLM仅在Plan（每次一次）、Test（每次计划条目一次）、Iterate（每次缺口一次）调用，Build阶段完全模板化无LLM参与。
- **规模跨度广的评估**：从单文件705行到97文件近28,000行的OpenTitan IP，覆盖外设与安全类设计，展示框架的泛化能力。
- **率先在OpenTitan安全IP上报告通过率与覆盖率**：作者声明这是首个在公开OpenTitan和IP安全块上报告这些指标的LLM DV研究。

## 8. 不足与局限

- **CSR级验证的根本边界**：当前流程聚焦寄存器级验证行为，对需要完整事务级序列的数据通路密集IP（AES、HMAC）无法实现覆盖率收敛。闭环保留的未覆盖区域无法通过寄存器级激励激活，需交易级（transaction-level）激励和更强参考模型。
- **通过率与覆盖率双指标的取舍不明**：论文承认"Qwen生成更多能存活的测试，而Claude生成覆盖更多RTL行为但稳定性差"的权衡，但未研究如何兼顾两者或自动选择最优策略。

Abstract —Register-transfer level (RTL) verification consumes a major part of modern system-on-chip (SoC) development effort. Yet, recent LLM-based verification-code generation often fails to produce runnable, design-consistent, and coverage-producing testbenches. We present AgentDV , a closed-loop agentic AI framework for automated RTL verification environment genera-tion. AgentDV transforms single-shot LLM testbench generation into a tool-grounded verification pipeline by combining LLM-guided analysis, testbench construction, simulation, coverage measurement, and iterative refinement. The framework intro-duces three key ideas: 1) runnability filtering to reject invalid generated environments, 2) CSR-grounded checking to reduce hallucinated signals and incorrect expected behavior, and 3) coverage-guided iteration to regenerate tests based on measured verification gaps. We evaluate AgentDV using three LLMs on challenge DUTs and public OpenTitan peripheral and security IP blocks. From our analysis, we observed that direct single-shot prompting fails to produce a valid coverage-producing environment on benchmarks. AgentDV achieves 100% pass rate on four DUTs and an average of 80.9% pass rate on all DUTs using Claude Sonnet 4.6. Similarly, an average of 58.7% and 60.6% pass rate is achieved for Llama and Qwen models, respectively. In addition, an average of 74.5%, 69.1%, and 64.9% of line coverage and 88.4%, 82.3%, and 76.7% of branch coverage for the benchmarks under consideration for Claude Sonnet 4.6, Llama, and Qwen models, respectively.

I. I NTRODUCTION 

Register-transfer level (RTL) functional verification has become a major bottleneck in modern system-on-chip (SoC) development as design complexity continues to increase. The engineering effort consumes about 50–60 % of total ASIC project time on design verification [1]. Although simulation tools and verification methodologies have advanced, RTL verification remains a highly manual and iterative process. This motivates automated RTL verification workflows that can generate executable tests, measure coverage, and refine the verification suite through feedback. Recent LLM-based RTL verification studies have be-gun to address this need by automating test generation and refinement, but verification environment generation for intellectual-property (IP)-level designs remains challenging. In addition, these works are also primarily evalu-ated on academic RTL benchmarks, such as VerilogEval and RTLLM [5], [6], leaving practical IP-level DV automation less explored. This gap is captured by the ISQED 2026 Agentic AI design verification challenge [8]. The challenge formalizes an autonomous RTL verification setting where an agent starts from RTL, a natural-language specification, and a CSR map. However, it defines the task rather than the solution. AgentDV is implemented using Verilator, cocotb, and pyUVM [9]–[11] with three LLM backends: Claude Sonnet 4.6, Llama 3.3 70B, and Qwen2.5-Coder 32B [12]– [16]. AgentDV is designed around the verification loop rather than during the code-generation step. The framework critically analyzes generated tests using deterministic design artifacts, checks runnability before admitting tests to the suite, measures line and branch coverage, and uses coverage feedback to guide additional test generation. A. LLM-Assisted RTL Verification 

Recent work has explored LLMs at different stages of the RTL verification flow. AutoBench [2] studies automatic testbench generation, CorrectBench [3] adds self-correction, and PRO-V-R1 [4] integrates tool feedback and reference-model-based checking. These approaches show that LLM-generated verification artifacts improve when generation is structured and connected to external feedback, rather than produced through direct prompting alone. Despite this progress, existing LLM-based DV flows still leave important parts of the IP-level verification environment unresolved. Testbench generation improves stimulus creation, but it does not by itself guarantee design-consistent check-ing. Reference-model-based approaches can provide expected behavior, but the reference model itself becomes part of the verification trust chain. If the reference model is incorrect, a generated test may pass even when the checking logic does not accurately verify the DUT behavior. Other works address complementary parts of the verification flow. LLM4DV [17] explores LLM-guided coverage-directed stimulus generation, while assertion-generation methods use LLMs to derive properties from design specifications [18]. UVM 2 [7] moves closer to environment-level automation by generating UVM components and refining tests using coverage feedback. However, complete subscriber/scoreboard and reference-model generation remain outside its core scope, leaving design-consistent checking as an open issue. Recent UVM-oriented systems such as HAVEN [19], UVMarvel [20], and ChatTest [21] further advance LLM-assisted testbench or verification-environment generation, but they target different generated artifacts, protocols, and benchmark suites. These limitations motivate an automated DV flow that connects generated stimulus with design-grounded expected behavior, runnability filtering, coverage measurement, and feedback-directed refinement. 

B. Autonomous Verification Task Setting 

The ISQED 2026 Agentic AI Design Verification Challenge provides a concrete task setting for autonomous DV automa-tion [8]. In the AutoVerifier task, an agent starts from RTL source, a natural-language specification, and a CSR register map, and must produce a verification environment that can execute tests, measure coverage, iterate on uncovered behavior, and report results. The task is organized into seven stages: ANALYZE , P LAN , B UILD , T EST , M EASURE , I TERATE , and REPORT .This setting is different from one-shot test generation. The generated environment must compile, run, check meaningful behavior, and support coverage-driven refinement under abounded execution budget. The task also emphasizes general-ization to unseen DUTs with a common TileLink-UL interface. These constraints motivate a flow that uses deterministic processing for design facts and uses LLMs where planning, reasoning, or test generation is needed. 

C. Register-Based Checking and RAL 

Register-based checking is a common foundation for bus-attached IP verification. A control-and-status register (CSR) map defines the software-visible behavior of the design, in-cluding register addresses, fields, reset values, and access policies. In UVM-style verification, a Register Abstraction Layer (RAL) represents this map as a software model. The RAL mirror tracks the expected value of each register field as the testbench performs reads and writes, and check-enabled reads compare the RTL response against the mirrored value. This mechanism is useful for LLM-assisted DV because register behavior should be derived from design artifacts rather than inferred by the model. If an LLM is asked to infer register addresses, field encodings, reset values, or access policies, hallucinated design facts can corrupt the checking logic. Deriving the register model from the CSR specification makes register addresses, reset values, field encodings, and access policies explicit and deterministic, providing a reliable first layer for automated verification. IV. A GENT DV F RAMEWORK 

A. Overview 

AgentDV implements the autonomous DV formulation de-fined in Section III. As shown in Fig. 2, AgentDV takes the input tuple I = ( R, S, M) and generates a verification package O. The pipeline is organized into two phases: a 

setup phase that prepares the verification environment from the input design artifacts, and an execution and closure phase that runs tests, measures coverage, iterates using feedback, and generates the final report. The remainder of this section describes the setup phase (Section IV-B), the execution and closure phase (Sec-tion IV-C), and the closed-loop coverage-directed iteration that drives gap closure (Section IV-D). 

B. Setup Phase 

The setup phase converts I into an executable verifica-tion environment E through three stages: Analyze , Plan , and 

Build . Analyze uses Verilator’s front-end and the OpenTitan 

reggen [22] library to extract a structured view from R and 

M, namely the port list, the TL-UL bus interface, and the register list with per-field access policies. Plan then invokes the LLM once with S and the register list to produce a YAML verification plan whose items are tagged with feature name, priority, and target coverage bin. Build is fully templated and mechanically generates the pyUVM RAL stack from the register list, namely a uvm_reg_block subclass with one uvm_reg per register and one uvm_reg_field per field, the TL-UL adapter that translates RAL accesses into TileLink transactions, and the environment wiring. The same stage generates a templated CSR test suite that exercises three canonical register behaviors: reset-value checks, multi-pattern read/write, and walking-one over every writable bit. All three call reg.read(check_t.CHECK) , so the mirror inside the RAL library, not the test code, supplies the expected value at every read. 

C. Execution and Closure Phase 

The execution phase takes the RAL stack and the templated CSR suite from the setup phase, runs the suite under simu-lation, and iterates on coverage. The final stage, Report , assembles the per-stage outputs into a Markdown summary, per-failure bug reports, and a structured JSON agent log. The two LLM-driven stages in this phase, Test and Iterate ,are bound at inference time to two deterministic tools: a retrieval-augmented index ( RAG ) that supplies targeted doc-umentation snippets when needed, and a runnability check (verify ) that validates every generated test before admitting it to the suite. The closed-loop dynamics and the runnability check are described in Section IV-D. 

D. Closed-Loop Coverage-Directed Iteration 

The Iterate stage closes the verification loop in AgentDV. After iteration k, Measure reports a coverage vector ck and an annotated set of uncovered RTL regions Uk. Iterate selects the next target region from Uk and prompts the LLM with that region and the register table to generate a gap-directed test tk+1 . The new test passes through the runnability check, runs through the cocotb simulator under Verilator, and is admitted to the suite only if it is runnable and contributes to coverage. The loop terminates after five iterations or af-ter two consecutive iterations without coverage improvement (max_iterations=5 , patience=2 ), which caps the per-DUT cost while preserving the closed-loop property. Two tool bindings keep each iteration grounded and runnable. Selective retrieval (RAG ) adds targeted snippets from a local document store covering the TileLink-UL proto-col, the cocotb APIs, the coverage APIs, and pyUVM usage; retrieval is gated on whether the prompt references a symbol the analyzed DUT does not define, so documentation context is added only when needed. The runnability check (verify )runs an ast.parse on the generated file and a single-test cocotb invocation under Verilator. It produces one of three outcomes, illustrated in Fig. 3: a pass admits the test to the suite; a Python crash appends the exception text to the next LLM call as concrete error feedback and retries once, discarding the file on a second crash; an assertion failure from a RAL reg.read(check_t.CHECK) call is retained as a verification finding, since it indicates a real mismatch between the hardware response and the mirror. This loop converts LLM-generated tests into simulation-validated and coverage-measured verification artifacts rather than admitting them as standalone generated code. V. E VALUATION

A. Experimental Setup 

We evaluate AgentDV on two RTL verification benchmark suites using three LLM backends. The flow uses Verila-tor 5.x for RTL simulation, cocotb 2.0 for Python-based co-simulation, and pyUVM 4.0 for UVM-style verification environment construction. The seven-stage AgentDV pipeline is orchestrated with LangGraph [23]. We evaluate three LLM backends: Claude Sonnet 4.6, Llama 3.3 70B Instruct AWQ, and Qwen2.5-Coder 32B In-struct AWQ [12]–[16]. Claude Sonnet 4.6 is accessed through an API backend, while Llama and Qwen are served locally with vLLM on a two-GPU machine with 48 GB of GPU memory. This setup enables a comparison between a strong cloud model and open-weight models using the same veri-fication process. The two open-weight models also utilize a RAL-aware prompt structure to address their limitations in following instructions related to register semantics. Prior LLM-based DV frameworks differ in the generated artifacts, tool flows, and benchmark suites, making direct numerical comparison misaligned. Our evaluation therefore focuses on two controlled comparisons: direct single-shot prompting versus AgentDV, and three LLM backends under the same AgentDV flow. The evaluated DUTs are summarized in Table I. The ISQED 2026 challenge benchmark contains compact single-file DUTs ranging from simple peripherals to cryptographic blocks. The OpenTitan benchmark is built from public OpenTitan periph-eral and security IP blocks and includes package, primitive, and shared dependency files. This split evaluates AgentDV on both controlled challenge designs and larger open-source RTL integration settings. All results are reported under a pass@1 setting. For each DUT and LLM, AgentDV generates one verification suite, and the suite is evaluated without retrying or selecting among multiple candidate suites. The closed-loop stage is limited to 

Kmax = 5 iterations with patience = 2 ; therefore, the loop stops after two consecutive iterations without coverage gain. A Claude-based AgentDV run completes in approximately 150 s at about $0.11 per DUT, while the locally served open-weight models require approximately 10–12 minutes per DUT. 

B. Evaluation Metrics

and case outcomes, are exercised. Thus, coverage measures whether the runnable test suite activates meaningful design behavior beyond simply executing without failure. AgentDV handles control-oriented IP more effectively than datapath-heavy cryptographic IP. The results from aegis_aes clearly highlight this lim-itation. All three LLMs remain near 37 % line coverage, although branch coverage is above 93 %. The generated tests exercise register decode, read/write behavior, and CSR-level control paths. However, the AES datapath requires a complete transaction sequence, including key loading, plaintext loading, engine start, status polling, and ciphertext observation. Since the current AgentDV flow focuses on CSR-level verification, the closed-loop feedback can identify the uncovered datapath logic but cannot fully activate it without protocol-level stimu-lus generation. The same observation applies to HMAC-style designs. SHA-256 compression logic is difficult to cover through isolated CSR accesses. Therefore, coverage improvement sat-urates even when the loop is allowed to continue. This result does not indicate that closed-loop iteration is ineffective. Rather, it shows the boundary of CSR-oriented test generation: the loop improves coverage when the missing behavior is reachable from the available stimulus abstraction, but datapath-heavy IP requires transaction-level sequences and stronger reference-model support. Overall, AgentDV is most effective for DUTs whose behav-ior is exposed through register-level control and status inter-faces. It generates stable and high-coverage tests for UART, GPIO, and timer-style blocks. For AES and HMAC designs, it still produces useful CSR verification suites, but full coverage closure requires protocol-aware stimulus and datapath-level checking. The contribution of closed-loop iteration is analyzed separately in Section V-D. 

D. Ablation Study 

This ablation evaluates the contribution of the closed-loop 

Iterate stage. Fig. 4 and Fig. 5 reports the iteration-wise contribution to line and branch coverage, respectively. In each stacked bar, the initial segment corresponds to the coverage obtained before feedback, while the remaining segments show the incremental coverage gained through closed-loop itera-tions. The results show that coverage feedback provides measur-able improvement beyond the initial test-generation step. In several cases, the first iteration gives the largest gain because the LLM receives concrete uncovered-region information from the first simulation run. Later iterations provide smaller gains as the remaining uncovered logic becomes harder to reach through the available stimulus abstraction or as the DUT approaches coverage saturation. The coverage contribution varies across DUTs. Peripheral-oriented designs such as bastion_gpio and 

warden_timer reach high coverage early, leaving limited opportunity for additional iterations. Other DUTs, including 

nexus_uart , aegis_aes , and sentinel_hmac ,show clearer incremental gains from feedback-directed test generation. This trend indicates that the Iterate stage is most effective when the remaining uncovered behavior is reachable through additional register-level scenarios. The AES and HMAC results clarify the boundary of the current implementation. AgentDV improves coverage for CSR-access behavior, register decode, and control/status logic. However, deeper datapath logic often requires complete protocol-level transactions and stronger expected-behavior modeling. As a result, later iterations may saturate even when uncovered logic remains. This observation supports the main scope of the paper: AgentDV establishes a reliable CSR-grounded verification layer, while protocol-level stimulus gen-eration and datapath reference modeling remain future work. VI. C ONCLUSION 

This work presents AgentDV, a closed-loop framework for LLM-assisted RTL verification environment generation. AgentDV combines LLM-based test construction with Ver-ilator, cocotb, pyUVM, and coverage-guided feedback to generate executable and interface-aware verification suites. Simulation results show that AgentDV generates runnable and coverage-effective verification suites across both compact and large RTL designs. With Claude Sonnet 4.6, AgentDV reaches 100 % pass rate on four DUTs and achieves 76.9 % line cover-age and 95.7 % branch coverage on the challenge benchmark. On the public OpenTitan benchmark, the framework achieves 71.6 % line coverage and 79.2 % branch coverage using only wrapper-level adaptation. The open-weight models remain competitive, reaching within 25 percentage points of Claude without API cost. The remaining coverage gap is mainly observed on cryptographic DUTs, where CSR-level stimulus cannot fully activate deep datapath behavior.

# Abstract 

Processor specifications underpin critical security and program-analysis tools such as disassemblers, decompilers, and emulators, yet, their correctness is rarely examined. Er-rors in specifications distort program behaviour, obscure vul-nerabilities, and enable analysis-evasion techniques. Val-idating processor specifications is a non-trivial task. Our study is a significant undertaking to enable, for the first time, the systematic validation of open-source SLEIGH language specifications, predominantly used by Ghidra . We design and implement a testing framework based on an automated ora-cle validation strategy by proxy . Our approach leverages the structure encoded in a specification itself to enumerate de-codable instruction forms and generate targeted initial states. Then differentially test the successful decoding and emulation of those instructions by comparing emulators exercising the processor specification against hardware references. Applying InSPECtor across diverse, open-source specifications— x86-64 , AArch64 , ARM/Thumb , RISC-V ,

MSP430 —embedding differences in specification styles, author preferences, and instruction set architecture designs, we uncovered over 38,920 discrepancies that led to 125 unique bugs with proposed fixes, identifying decoding and semantic defects as well as cross-vendor inconsistencies. We distill our findings into 8 concrete recommendations to drive future improvements. Our work underscores the importance of specification correctness and provides a practical tool to substantially improve the fidelity of SLEIGH processor specifications, strengthening the reliability of downstream security and analysis tools. 

# 1 Introduction 

SLEIGH is a domain-specific language (DSL) for describing processor specifications that decode and translate instructions into the architecture-agnostic intermediate representation (IR), Pcode [38]. There are over 35 processor families expressed in 

SLEIGH specifications, covering a diverse range of processors from PIC microcontrollers to modern x86-64 and ARM/Thumb .Significantly, SLEIGH specifications underpin Ghidra [37], the dominant open source multi-architecture tool-chain for re-verse engineering and binary analysis, and multi-architecture emulators such as Alligator from AirBus [10], Icicle [8], MetaEmu [7] and Styx [22]. In Ghidra’s disassembler and decompiler, SLEIGH specifications directly determine how binary code is decoded, lifted, and interpreted by analysts and automated scripts. As a result, SLEIGH specifications sit on the critical path of security workflows such as vulnerability discovery, malware analysis, fuzzing, firmware auditing, and program understanding. This widespread reliance amplifies the consequences of specification errors: flaws in SLEIGH can propagate across multiple tools, users, and workflows. Yet, despite this central role, the reliability of SLEIGH specifications remains an under-explored problem. In practice, SLEIGH specifications are large, painstakingly constructed artifacts that encode both instruction formats and their semantics. Developing faithful processor speci-fications is a non-trivial task. For instance, the ARM man-ual is 12,000 pages where complexities such as the operand dependent behavior of instruction mnemonics negates sim-plistic examination of mnemonics. Additionally, the 2025 edition of the Intel Software Developer’s Manual [1] ex-ceeds 5000 pages. The specifications must capture subtle architectural behaviors across diverse and often poorly doc-umented instruction set architectures. Further, to address the demand for rich, fast and safe computation, modern ar-chitectures are constantly evolving, with new instructions and features added each year 1, translating to an increase in instructions and complex instruction-bit encodings in ISAs. The painstaking construction and update of specifications to integrate architectural changes whilst maintaining backward

1arXiv:2608.13042v1 [cs.CR] 13 Aug 2026 compatibility makes the specifications intrinsically suscepti-ble to bugs. Even small mistakes—such as incorrect operand decoding, missing side effects, or inconsistent semantics can propagate silently through static and dynamic analysis tools. These errors may lead to misleading decompilation output and unsound program analyses, ultimately undermining the conclusions drawn by security practitioners; often exploited by malware to detect virtual environments [6] and hide from analysis [30, 34, 35]. Importantly, the critical dependency on SLEIGH specifi-cations has not been met by a commensurate, open source assurance of its correctness. Therefore, we are motivated to improve the correctness of SLEIGH processor specifications. By enhancing the veracity of SLEIGH processor specifi-cations, we expect to drive improvements across all their applications. 

The Study. In this first study, we expend our effort to improve the veracity of the SLEIGH processor specifications with the hope of generalizing our learning outcomes to broader speci-fication assurance research. Importantly, these specifications need to be updated and reassessed for correctness as ISAs evolve and new instructions are added. Our efforts will facili-tate testing implementations thoroughly, and automating this process in the future. Previously, studies have examined improving the correct-ness of CPU emulators [24–26,39], hypervisors [3], processor hardware [17, 33, 36], disassembly veracity (textual represen-tation accuracy) [18,29], while a few have tested the semantic correctness of binary lifters [9, 19] but specification level cor-rectness has received less attention. Although the work in [27] considered usability of Pcode for formal analysis and the au-thors in [4] made significant strides to validate the veracity of Sail specification language described semantic models for significant parts of ARMv8-A , RISC-V , and CHERI-MIPS , the correctness of the extensive multi-architecture support within the SLEIGH specifications have not been examined. In seeking to design an approach to uncover specification bugs, we observe that a processor specification itself encodes enough structure to drive systematic validation. So, we in-troduce InSPECtor , a framework that automatically traverses

specifications to enumerate decodable instructions, derive targeted execution states from semantic definitions, and perform differential testing against hardware reference systems. This enables high-coverage, specification-driven testing without redundant instruction exploration.

In summary: • We propose symbolically traversing SLEIGH specification decoding rules, a new, systematic methodology that aims to exhaustively generate instruction encodings, extracting edge cases for testing and deriving initial input states that trigger these edge cases. • We design, implement, and evaluate the methodology in the prototype InSPECtor system for testing specifications, including, GenSYS —a test case generation tool that inte-grates these techniques and JuxtaPlayer —a robust differ-ential testing environment capable of executing test cases on both emulators and hardware-assisted virtual machines. • We analyze the discovered bugs, identify their root causes, propose fixes, and distill 8 recommendations for improving the SLEIGH DSL to prevent future issues. Employing a SLEIGH specification for decoding begins with two inputs: a sequence of bytes (the instruction encoding) and a set of context bits. Context bits are a SLEIGH -specific mechanism used for two purposes: i) to encode information relevant to decoding that is not directly present in the instruc-tion encoding, such as the current processor mode (e.g., ARM 

vs. THUMB ); and ii) to transfer information between construc-tors. For example, context bits are often used to alter operand decoding in the presence of prefix bytes. Given this initial state, the decoder attempts to find a con-structor whose pattern section matches the current state. Con-structors are considered from most to least specific, where specificity is determined by the number of constrained bits in the pattern section 3. If no constructor matches, the encod-ing is treated as undecodable or invalid. When a match is found, the decoder applies the corresponding decode actions to update its state. It then recursively evaluates any subta-bles referenced in the pattern section using the updated state. Constructors in each subtable are matched and evaluated in the same way until the instruction is fully decoded. Once decoding is complete, the instruction semantics can be deter-mined by evaluating the semantic section of the constructors matched during decoding, potentially substituting subtable references with the values exported by the corresponding constructors. # 3.1 Instruction Generation 

For SLEIGH specifications, generating all instructions with unique semantics is equivalent to generating one instruction for each possible decode path in the specification. We can do this by determining which constraints on the instruction encoding must hold for a given constructor to be selected dur-ing decoding, and then solving those constraints to produce a concrete instruction encoding. Conceptually, this process can be viewed as a constraint satisfaction problem (CSP). In practice, however, efficiently collecting and solving all relevant constraints requires a com-plex traversal of the decode tree. In particular, the traversal must handle several kinds of constraints, account for implicit constraints introduced by overlapping constructors, manage decode actions that modify decoder state during traversal, and avoid unbounded recursion. Deferred constraints are additional constraints on the in-struction bit vector that cannot be resolved to a fixed value (e.g., inequalities). These constraints are solved simultane-ously after the traversal process has completed and all con-straints are known. By maintaining known instruction bits separately from deferred constraints, the algorithm can ef-ficiently test satisfiability during traversal and prune large portions of the search space. For example, if a constructor in a subtable requires a particular bit to be 1, but that bit is already known to be 0 from an earlier constraint, then the corresponding subtree can be discarded immediately, signif-icantly improving efficiency. Next, we detail the complex component of the method employed in the instruction genera-tion algorithm design. 

3.1.1 Translating Constructor Constraints 

The following sections describes the method for translating the pattern section of each constructor into a combination of fixed bit patterns and deferred constraints encapsulating the TRANSLATE function in Algorithm 1. 

Simple constraints. Most constraints involve equality checks between a constant and a range of instruction or context bits. These constraints can be translated directly into fixed values for the corresponding bits in the instruction or context bit vector. If a new constraint is unsatisfiable given the previously fixed values, traversal stops and the algorithm continues with a different set of constructor choices. Otherwise, the newly constrained bits are updated and traversal continues. 

Example. Using specification in Figure 1, consider the run 

constructor on line 12 and the corresponding Op subtable: 12 :run Op is op =0 & Op { HwOp(Op); } 1 Op: "nop" is op =1 & i16 =0 { export 0; } 2 Op: "syscall" is op =0 & i16 =1 { export 1; } ... 

When the :run constructor is selected, the algorithm up-dates the instruction bit vector so that the bits correspond-ing to the op field are fixed to 0. It then attempts to select a constructor from the Op subtable by checking each con-structor’s constraints against the current instruction bit vector. The Op:"nop" constructor requires the op field is equal to 1, which conflicts with the current value of 0, so it is immedi-ately discarded. The Op:"syscall" constructor is compati-ble with the current instruction bit vector, so it is selected and traversal continues with the i16=1 constraint specified by the constructor. All simple constraints can be reduced to a bitwise mask-and-compare operation. For example, when generating an instruction corresponding to run syscall , the final set of constraints passed to the SMT solver is (i & 0xfffffe00 == 0x00010000) , where i denotes the instruction bit vector. 

Complex constraints. Beyond simple equality constraints, 

SLEIGH also allows constructors to use more complex con-5straints to match instructions. This includes both inequalities and constraints involving non-constant expressions. Unlike simple constraints, there is often no single value that can be as-signed to the constrained bits to satisfy the constraint outright. One possible strategy would be to choose any value satisfying the constraint and continue traversal; however, such a choice may conflict with constraints introduced by later subtables, preventing valid instructions from being generated Another option would be to exhaustively explore all possible values, but this would require traversing an excessive number of paths and would generate many redundant instructions Instead, we elect to check that such constraints are potentially satisfiable (i.e., they do not already conflict with the existing simple constraints) and then add them to a list of deferred constraints, which are solved once traversal is complete. Once constructors for all subtables have been selected, the full set of constraints for the current instruction is known. To obtain a final instruction encoding, a symbolic expression is constructed from the instruction bit vector together with the deferred constraints. This expression is then passed to an SMT solver (Z3), which attempts to find a concrete assignment to all bits satisfying the combined constraints. If the solver succeeds, it returns a concrete instruction encoding; otherwise, it reports that the constraints are unsatisfiable. 

Example. As an example, consider the :nop constructor from line 14 of our example specification in Figure 1: 14 :nop is op =1 & rd = rn & Imm0 { } 

For an instruction to match this constructor, the rd and 

rn fields must be equal. This constraint cannot be trans-lated directly into fixed values for the instruction bit vector, since there are many possible values for rd and rn that sat-isfy it. Rather than choosing an assignment prematurely, we add the constraint rd = rn to the list of deferred con-straints. At the end of traversal, the final constraint passed to the SMT solver would therefore be ‘ (i & 0xfffffe00 == 0x00000200) && (i.rd == i.rn) ’. To optimize the process further, we check whether deferred constraints remain potentially satisfiable given the currently known bits. Suppose there is a deferred constraint ‘ i16 > 0 ’. The algorithm then checks whether at least one bit in the range corresponding to i16 is either unknown or equal to 1. If a different constructor requires that i16=0 , we can immediately reject it due to the ‘ i16 > 0 ’ constraint, which avoids wasting time traversing impossible constructor combinations. 

Constraints imposed in attachments. Fields referenced by a constructor may be linked to attachments that control the interpretation of the underlying bits. While most attachments allow all field values, some SLEIGH specifications use attach-ments to mark certain operand values as invalid. To handle this during instruction generation, invalid values are excluded by introducing appropriate deferred constraints. 

Example. A possible set of attachments for our example specification in Figure 1 is as follows: attach variables [rd rn] [ _ r1 r2 r3 r4 r5 r6 r7] 

Whenever rd or rn appears unconstrained in the specifi-cation (e.g., in the :mov and :addi constructors), its value is interpreted according to the attachment mapping. For ex-ample, ‘ rd=1 ’ corresponds to r1 ; ‘ rd=2 ’ corresponds to r2 ,and so forth. In this example, an attachment index of 0 has no associated register, indicated by the ‘ _’ operator. To account for this, we treat such cases as implicit complex constraints: ‘rd != 0 ’ and ‘ rn != 0 ’. For instruction generation, these constraints are handled in the same way as other complex constraints discussed previously. 

Implied constraints from overlapping constructors. The behavior of an instruction is primarily determined by its ‘op-code’ field, 7 which specifies the operation performed on the instruction’s operands. In general, two instructions with the same opcode have the same semantics regardless of their operand values. However, some instructions can be repre-sented as a specific sub-encoding of a more general instruc-tion. For example, copying a value between registers (e.g., 

mov r0,r1 ) is semantically equivalent to adding zero to a source and storing the result in a destination register (e.g., 

addi r0,r1,0 ). These instructions are often referred to as ‘pseudo-instructions’, and many ISAs use them to reduce redundant encodings. Although SLEIGH specifications could ignore pseudo-instructions and always decode them as their generic coun-terparts, modeling them explicitly benefits both human and machine analysis—A more specific textual representation im-proves disassembly for human analysts, and defining special-ized semantics can simplify both static and dynamic analysis. In addition to pseudo-instructions, some ISAs include in-structions with more complex operand encodings that require special handling during decoding. For example, in both x86-64 and MSP430 , instruction encodings include ‘addressing mode’ bits that alter the interpretation of operand fields. To model such encodings, SLEIGH provides a mechanism known as constructor specialization, which allows multiple constructors within the same subtable to match the same instruction encoding. Recall (Section 2), the SLEIGH de-coder prioritizes matching constructors from most to least constrained. Consequently, for an instruction to match a less constrained constructor, it must also avoid matching any overlapping constructors that would be considered first. This behavior must be modeled during generation to ensure that the generated instruction encoding matches the intended construc-tor. To do so, we treat the target constructor as if it carried an additional implied constraint requiring all preceding overlap-ping constructors to not match.

Notice that when we add constraints to resolve the overlap with the :nop constructor, we allow the overlap to be resolved either by negating the simple constraints or by backtracking, maximizing the flexibility the solver has to generate an en-coding, allowing the algorithm to generate addi r0,r0,1 .

Self-referencing constructors and decode actions. SLEIGH 

allows constructors to be self-referencing , meaning that a con-structor may reference the same subtable to which it belongs. This functionality is used for two main purposes: i) phased decoding and ii) optional prefix parsing .In both cases, the self-referencing constructor must be able to influence subsequent steps of the decoding process. To sup-port this, constructors may specify decode actions in square brackets after the pattern section. Each decode action eval-uates an arithmetic expression, possibly over context and/or instruction bits, and writes the result to a field in the context bit vector. 

Phased decoding. For phased decoding, context fields are used to split the decoding process into multiple phases, where previous phases can set context bits that are used as constraints in later phases. During instruction generation, this mechanism is straight-forward to handle; at any point in the traversal, the phase has a fixed value, so only constructors for the current phase need to be considered. Phased decoding is not used in our example specification but we provide the following example (inspired by the AArch64 specification) to explain.

4.2.2 Decoding Issues 

In general, decoding issues occur when incorrect constructor constraints prevent the correct instruction implementation from being selected. We detail these in the following. 

I-1 Redundant and out-of-order prefixes. Instruction pre-fixes are one of the most complex aspects of x86-64 instruc-tion encoding and causes discrepancies between hardware vendors (see Section C), security-critical CPU bugs [28], and severe performance issues [13]. Similarly, the x86-64 SLEIGH 

specification contains many prefix-related decoding issues.  

> x86-64

instructions allow redundant and duplicate prefixes; however, the SLEIGH implementation assumes that at most one of each prefix is present. For example, when multiple operand-size ( 66 ) or address-size ( 67 ) override prefixes ap-pear, the specification misinterprets these prefixes, leading to discrepancies. Additionally, the 64-bit extension to the ISA introduces a new class of prefixes (the REX prefix) with different decoding rules compared to legacy prefixes. According to the ISA reference, there must be at most one REX prefix present, and it must follow all legacy prefixes. However, both the Intel and AMD CPUs tested are more lenient during decoding; any REX prefixes that precede legacy prefixes are ignored, and they allow multiple REX prefixes, only using the final one. The SLEIGH specification does not replicate this behavior; instead, it rejects all instructions where there are multiple REX prefixes, or the prefix is not the last one. While compilers avoid emitting unnecessary prefixes, thus reducing the impact of this issue on real-world code, such prefixes occasionally appear in handcrafted assembly for low-level performance optimizations. For example, OpenSSL uses redundant prefixes to align code to micro-architecturally friendly boundaries [2]. 

I-2 Context handling issues. An earlier version of the x86-64 SLEIGH specification used a single context field for both indicating whether long mode (64-bit) instructions were de-codable and for tracking the current address size. This design assumed that long mode could be inferred from the address size, because it has a different default setting compared to other processor modes. However, including an address-size override prefix ( 67 ) changes the current address size, caus-ing the specification to mistakenly assume that the processor is not in long mode. Although the specification was later refined to introduce a dedicated context bit for long mode, many long mode instructions still reference the operand-size bit, resulting in discrepancies. 

I-3 Overlapping constructors. Some constructors are un-reachable because every instruction encoding that matches them is instead matched by a different constructor (with differ-ent semantics). Further analysis revealed that many overlap-ping constructors are under-constrained . This bug causes the wrong instruction semantics and disassembly to be used for the instructions associated with an unreachable constructor. 

I-4 Over constrained constructors. Several constructors have additional constraints that are not present in the underly-ing ISA. For example on x86-64 , two constructors require a specific bit in the decoder context to be matched. However, this bit is only set in 32-bit protected mode, even though the associated instructions are also valid in 64-bit long mode. This issue likely stems from a mismatch in the way context bits are used in the SLEIGH specification. On real hardware, the protected mode bit is set in long mode, but the SLEIGH 

specification only sets an equivalent bit when configured for 32-bit mode. The impact of this bug is that the corresponding instructions are incorrectly treated as invalid in long mode. 

I-5 Constructor ordering. For x86-64 specifically there was also several issues related to constructor ordering. Two unreachable constructors, corresponding to 64-bit variants of instructions, share the same encoding as their 32-bit coun-terparts, except for a mandatory REX.W prefix. However, the 32-bit variant allows the prefix to be present and is always matched first, preventing any encoding from matching the 64-bit variant. This bug likely originates from unclear ordering rules. Since the 64-bit variant is not strictly more constrained than the 32-bit variant, the decoder defaults to the declara-tion order. This issue causes the wrong register sizes (32-bit instead of 64-bit) to be used for the instruction, resulting in incorrect disassembly and semantics. 

4.2.3 Semantics Ordering Issues 

I-6 Semantic ordering issues arise when correct outcomes are dependent on a specific order of operations which are not followed. This was common in the MSP430 ISA which makes heavy use of addressing modes to augment its basic instructions. These modes include direct and offset indexing, and address auto incrementing among others. All of which are available to the MOV instruction leading to cases such as MOV.W @R7+, 0x0(R7) . The MSP430 was found to execute this instruction by resolving and incrementing the source register, before resolving the destination, performing the instruction’s operations with the pre-incremented value, and writing back the result. This causes loading the destination 0x0(R7) to be impacted by the increment of the source @R7+ . This differed from the SLEIGH implementation which always performed the increment as the last operation of the instruction. This also occurred in pseudo-instructions such as POP.W SP (MOV.W @SP+, SP ) even though they had separate Pcode semantics. Semantic ordering issues where also found outside of ad-dressing modes in AArch64 . The NGCS instruction’s output was written to the destination register, and then the flags where calculated off that registers value. However when us-ing the zero register as the destination register no write is 13 performed, and the flags are always incorrectly calculated from the fixed value of zero. 

4.2.4 Incorrect Semantics Issues 

Incorrect or missing semantics bugs appear when an imple-mentation uses the incorrect operations, or does not imple-ment all behaviors of an instruction. This was the largest cate-gory of bugs, but also contained the most subtle and unique mistakes. For example in AArch64 the BCAX instruction per-formed an or operations instead of an xor , and STLRB stored a word sized value instead of byte. In addition to these subtle issues, there where several wider classes of issues. 

I-7 Missing floating point semantics. The RISC-V floating point extensions encode smaller precision floats as NAN-boxed inside the larger registers, by setting all the unused upper bits to 1’s. However, the SLEIGH specification does not use this encoding for single precision floats when writing to the registers, nor does it propagate un-NAN-boxed values as NAN’s, causing all initial floating point test cases to fail. The extra logic that fixing this issue added to the start and end of all floating point instructions was not able to be filtered out by Ghidra ’s decompiler, causing the decompilation to become bloated. 

I-8 Default values and behaviors. RISC-V defines specific result values for arithmetic exceptions. On divide by zero the division instruction should return 2 width − 1, and the remain-der should be the dividend. Currently there is no zero check before the division, resulting in this behavior being dependent on the execution environment default. 

I9 Incorrect register lists. To implement instructions oper-ating on groups of registers in SLEIGH , recursive subtables are used where the different constructors conditionally in-clude the Pcode semantics for that register. This occurs in 

> MSP430

, AArch64 , and ARM/Thumb , with MSP430 having an issue where it did not correctly handle register wrapping, and ARM/Thumb having an issue where the registers where pushed in the wrong order. However, this style of imple-mentation inherently requires duplicated sets of constructors based on the number of registers, requiring the same fix to be applied to each constructor in the set. 

4.2.5 Aliasing Issues 

I-10 The SLEIGH specification implements instructions us-ing multiple Pcode operations, and when the source and desti-nation operands refer to the same register or memory location, incorrectly ordering these operations can result in incorrect semantics. This issue is often observed in the implementa-tion of SIMD instructions ( x86-64 , ARM/Thumb ), where the destination register is frequently modified before the source register is fully read. For RISC-V this occurs in the Control and Status Register extension in the FSCSR /FSFLAGS /FSFRM instructions. These instructions swap a value into the float CSRs by moving the source register to the CSR and the value in the CSR to the destination register. The Pcode implementation of this instruction attempted to do this without using a temporary, causing the value in the source register to be overwritten. This lack of a temporary when using aliased registers also occurs in the compressed instruction extension with the C.JALR ra 

instructions. This instruction should jump to the address held in the ra register and replace its value with the address of the following instruction, but was found to instead execute the instruction at the following address. Additionally in both RISC-V and AArch64 the zero register must always read the value 0, and writes to the zero register must be ignored, both contain bugs. The RISC-V SLEIGH 

specification handles these cases by using a subtable to ex-port a temporary variable instead of the zero register. Many instructions do not do this and instead directly reference the zero register. This allows the instructions to write non-zero values to the zero register when it is used as a destination. The destination register for some instructions is intended to be 32 bits instead of the full register width. To handle this, a constructor rdW is used, which creates a temporary of the right size, sets its value to that of the destination register, and exports the temporary. When an instruction attempts to write to this aliased register, it would change the temporary but not the destination register. This prevented the FCVT instructions from outputting any result. 

4.2.6 Unresolvable Issues 

The problems we discussed previously can be addressed through careful editing of processor specifications. How-ever, there are numerous issues requiring more fundamental design changes to simultaneously support accuracy of both decompilation and emulation use cases; we discuss these next. 

I-11 Unimplemented operations. The SIMD and vector instructions across x86-64 and AArch64 are partially imple-mented in Pcode and partially with added custom Pcode ops, with the semantic section of RISC-V ’s vector extension com-pletely unimplemented. A full Pcode implementation of these is possible, but would bloat the generated disassembly, and output Pcode for static analysis tools. 

I-12 Floating point issues. Floating point instructions con-tributed to a large number of discrepancies as many of the features which architectures use of the IEEE 754 standard are not exposed at the SLEIGH level. Architectures with hardware support for floating point numbers generally include the common encodings of FP32 and FP64 which are supported in SLEIGH . # 5 Discussion 

In addition to the limitations of this work and potential for future work, potential changes to the design of the SLEIGH 

specification language are discussed below. These suggested changes allow for improved maintainability, versatility, fi-delity and understandability of SLEIGH specifications. 

# 5.1 Recommendations for Improving SLEIGH 

The SLEIGH language is demonstrably effective for specify-ing instruction semantics, Ghidra has over 35 ISAs expressed in SLEIGH . However, our study reveals that SLEIGH lacks features and constructs needed to express complex instruction behaviors suited for its applications in security workflows. Based on the issues uncovered in differential test result anal-ysis in Section 4.2, we propose extensions to the SLEIGH 

language that could potentially lead to fewer bugs in specifi-cations. We codify these broadly in: i) General recommenda-tions based on the issues we uncovered in Section 4.2.2-4.2.5. These aim to better support the key use cases for SLEIGH 

whilst reducing the incidence of bugs when authoring and maintaining specifications; and ii) Recommendations to ad-dress the unresolvable issues identified in Section 4.2.6. 

5.1.1 General Recommendations 

The modifications to SLEIGH described here mainly aim to improve its expressiveness and usability to reduce bugs when authoring and maintaining specifications. 16 #1: Provide for decompiler hints 

Adding support for decompiler hints can enable high-fidelity SLEIGH specifications to improve both emulation and decompliation. Interestingly, as the fidelity of the SLEIGH semantics im-prove, the readability and overall quality of the resulting de-compiled code can, in some cases, actually decline. These readability regressions typically arise from specific, rare edge cases that compilers guarantee cannot occur, but which the decompiler is unable to reliably rule out. Examples include handling offsets to 20-bit addresses on MSP430 or differences in the bit-level representation of NaN values. Introducing de-compiler hints—such as annotations indicating that certain conditions are likely—would allow high-fidelity Pcode to be retained for emulation, while still enabling the decompiler to make simplifying assumptions that improve decompilation quality. Decompiler hints can ensure a specification is simul-taneously accurate and useful for decompilation to provide a more effective solution to issues such as I7 and I8 . 

#2: Design templated constructors and arrays 

Add complex language constructs to reduce manual code duplication and copy-paste bugs, & improve readability and maintainability of specifications. Often, the same issue in one constructor is repeated in oth-ers due to duplicate logic in the specification. Multiple issues have resulted from these copy-and-paste type duplications, such as the issues we fixed identified in I9 . This code dupli-cation is partly necessitated by the limited expressiveness of the SLEIGH language, particularly in representing loop and array-like constructs. When an instruction requires a repeated action, such as assigning values to a list of registers (as seen in Listing 1), the only available option is to manually write each assignment. This not only contributes to bugs when writing specifications, but also makes the specification harder to read and maintain. Consequently, complex instructions are sometimes left unimplemented, as found in I11 . This issue could be addressed by extending the SLEIGH language to support defining arrays and templated constructors. Possible syntax for this extension is shown in Appendix H, featuring a template for the reglist constructor with the variable i used for indexing into arrays to obtain both the constraints for the templated constructor and the target register. 

#3: Design accessor functions 

export statement behaviors are error-prone. Design logical accessor functions for exporting values to manage dependencies. To pass information between subtables, SLEIGH allows the semantics section to return a reference to a value, variable, or memory location using an export statement (the final statement of the section). But, due to the subtleties of how this statement operates, using export statements can be error-prone and contribute to non-obvious aliasing issues such as those reported in I10 accounting for 9 out of the 125 bugs. A major subtlety is that the export statement is not evalu-ated alongside the rest of the semantic section; instead, it is evaluated at the point it is referenced in the semantic section of the parent constructor. Consequently, copying a register’s value to a temporary and then exporting the temporary be-haves differently from exporting the register directly. For example, in bugs discovered in the x86-64 specification with aliasing issues, the SLEIGH specification code modifies the register in the main constructor, not realizing that the mod-ifications also affect referenced registers in subtables. This could be avoided by introducing more logical accessor func-tions for exporting values—for example, forcing the use of temporaries—or by introducing warnings when a potential reference overlaps with a register modified in the parent con-structor. 

#4: Move to inline helper functions 

Support both decompilation and emulation needs by facil-itating runtime selection of the desired instruction fidelity with inline helper functions.  

> SLEIGH

currently relies on black-box functions—e.g. 

define pcodeop <name> —for instructions that are too com-plex to model using Pcode or not fully implemented as we have come across in issues such as I7 and I8 and partially implemented SIMD and vector instructions identified in I11 . The desire is to eventually replace these black-box functions with Pcode semantics; however, in rare cases the opposite oc-curs; black-box functions are used to replace Pcode semantics. For example, the Pcode semantics for the x86-64 instruction 

FXSAVE were replaced with the black-box _fxsave opera-tion, matching the compiler intrinsic used in C to generate the instruction. This simplifies decompilation but prevents its use for emulation. To facilitate dynamic selection of the desired fidelity of instruction semantics, we propose mov-ing to inline helper functions. For example, an emulator can maximize instruction fidelity by handling every edge case, while decompilation could represent the code as an intrinsic function. 

5.1.2 Recommendations to Address Unresolvable Issues 

To address problems that are infeasible or impractical to resolve under the current SLEIGH rules, as identified in issues I11 – I14 , we propose the following specific recommenda-tions to extend the SLEIGH DSL. 

#5: Provide for SIMD extensions I11 

Mapping SIMD semantics to Pcode in the SLEIGH DSL is cumbersome due to the many near-identical operations used. Introduce vectorised Pcode operations or structured looping constructs to express SIMD instruction seman-tics. Modern ISAs increasingly add instructions for working 17 with lanes of data—e.g. SIMD and vector instructions—yet expressing their semantics in SLEIGH is cumbersome and error-prone. Consequently, we observe poor decompilation quality and a track record of bugs in the subset of instructions that have been defined. However, as these instructions are adopted by more programs, strong support in SLEIGH specifi-cations has become a necessity. Further, we take the extensive use of custom Pcode operations and the partial SIMD imple-mentations we found as a sign that a new group should be added to the Pcode instruction set for SIMD operations. Decompilation could be partially improved by allowing the decompiler to hide internal details with the inline helper functions described previously; however, this may not benefit advanced decompilation techniques such as de-vectorization— i.e., translating a sequence of vector instructions back into a loop over scalar elements. Introducing new vectorized Pcode operations would make expressing SIMD constructs simpler, although this requires any analysis dependent on Pcode to also account for the new operations. Alternatively, more structured looping constructs could be introduced to SLEIGH ,which could be automatically unrolled for unstructured analy-sis while being accounted for during decompilation. 

#6: Provide floating-point operation descriptions I12 

Design structures to encode floating-point operations and rounding modes. The minimal set of floating-point operations described in  

> SLEIGH

are insufficient to precisely capture the complete behavior of floating-point instructions supported in modern ISAs. There are no Pcode operations for performing unsigned conversions between integers and floating-point values, and no method to encode different rounding modes. Adding new Pcode operations for floating-point conversions and rounding modes would allow the SLEIGH specification to be more precise. However, this would require any analysis that uses Pcode to be updated to account for new operations. This is a significant drawback, as it requires modifying all existing analyses and tools that rely on Pcode. Alternatively, many of the semantics could instead be encoded as hints—similar to the existing branch hints—which would allow tools, such as a decompiler, to selectively ignore new operations, treating them as more generic cases. 

#7: Explicit unpredictable/undefined values I13 

Allow better handling or precise isolation of undefined or unpredictable outputs in ISAs. A considerable number of discrepancies across all archi-tectures arise from differences in outputs that are designated as undefined or unpredictable in the ISA reference. Many of these also lead to discrepancies between different hard-ware implementations of the same ISA. A remedy is to add a single new Pcode operation to annotate registers that have unpredictable values. This would allow discrepancies due to these operations to be isolated more precisely, enable analy-sis tools to identify program portability issues, arising from either compiler bugs or manually written code, and assist in analyzing malware that exploits such discrepancies to detect the execution environment. 

#8: Alignment requirements for memory opera-tions I14 

Introduce explicit inclusion of alignment information to memory operations. Currently, SLEIGH only supports specifying a global align-ment for all memory operations within an ISA; this can lead to discrepancies in the exception state after executing instruc-tions in emulation with stricter alignment requirements. Ad-justing the Pcode L OAD /S TORE operations to include align-ment information or introducing new naturally-aligned mem-ory operations are possible resolutions. Provisions for opera-tion level alignment can improve emulation accuracy. This alignment information is also useful for static analysis, such as detecting potentially unaligned accesses, improved type inference, and enabling constant propagation algorithms to make assumptions about the value of registers holding aligned pointers. 

# 5.2 Other Processor Specifications  

> InSPECtor

is designed to address the challenges posed by the SLEIGH DSL in its extensive and diverse set of proces-sor specifications but its core ideas—symbolically traversing a specification’s decoding rules, extracting edge cases and state generation—can extend to other specification languages such as Sail or VADL. At a high level, languages such as VADL [15] and Sail [32] share structural similarities with SLEIGH: they describe instruction encodings alongside exe-cutable or interpretable semantics. VADL, as implemented in OpenVADL [15], provides a concise and formal repre-sentation of processor architectures, with explicit modeling of instruction formats and behavior. Similarly, Sail [32] of-fers a rich, formally grounded language for ISA semantics, often used in verification settings for architectures such as ARM. These commonalities suggest that our approach could generalize along two main dimensions. First, specification traversal—i.e., systematically enumerating decoding paths, instruction variants, or semantic rules—can be adapted to any language that exposes structured instruction definitions. Second, symbolic solving can be applied as long as the speci-fication can be translated into a constraint representation. In principle, both VADL and Sail provide sufficient structure and formalism to support these operations. However, adopting our approach requires solving chal-lenges pertinent to the specification language, and traversal in each specification language is fundamentally different be-cause each language exposes different normalized represen-tation and structure. In particular, more formally grounded specification languages such as Sail support richer decoding constructors (e.g., complex control flow), which can signif-18 icantly increase solver complexity or introduce path explo-sion during specification traversal, requiring more aggressive pruning or summarization. Then, translating semantics into efficient encodings for a symbolic solver could be non-trivial, if the abstractions do not map directly to bit-precise con-straints. Consequently, the primary effort is likely to lie not in redesigning the symbolic methodology itself, but in bridg-ing language-specific representations into a model suitable for constraint solving and automated exploration challenges posed by the specification language’s descriptions of proces-sors. 

# 5.3 False Positives 

In general, discrepancies correspond to either bugs or lim-itations in the SLEIGH specification, thus defining a false positive is hard. Each discrepancy identified represents a pos-sible bug, but cannot be easily deduplicated without manual effort, so we report discrepancies, as done in related works in CPU emulator testing [24–26]. Then, we discuss bugs in the context of root-causes fixed, not the number of buggy instructions, a more inflated number. The large number of discrepancies found for many of the identified bugs is a major contributor to the observed differ-ence between the bug and discrepancy counts. In addition to discrepancies mapped to root-causes, other contributors in-clude ISA-defined unpredictable behaviours, unimplemented semantics, or issues which cannot be fixed without extending 

> SLEIGH

, discussed further in Section 4.2.6. Due to limitations of the SLEIGH language, these issues do not represent an error in the specification, and consequently could be considered false positives; however, our recommendations for improving 

> SLEIGH

, discussed in Section 5.1, would allow addressing the sources of these discrepancies while helping to improve specification veracity. 

# 5.4 Limitations & Future Work 

Despite our extensive efforts, our work is not without limita-tions. Although we sought to test the correctness of a spec-ification, our approach will not determine the completeness of a specification. Because in the specification-driven ap-proach, instructions missing from a SLEIGH specification are not tested. However, these instructions exhibit a well-defined failure mode: whenever an unknown instruction encoding is encountered, an invalid instruction exception will be gener-ated in, for instance, SLEIGH -based emulators. This behavior typically makes any missed instructions easy to detect in real-world targets. But, in disassemblers, missing instruc-tion in specifications can impact control-flow recovery where invalid instructions are used as heuristics for identifying un-reachable or invalid code regions. In these cases, missing instructions may cause the analysis to misattribute control-flow errors, making it harder to localize the root cause. Future work should consider not only correctness but also achieving completeness attributes to specification testing. Some ISAs include instructions that alter the execution of subsequent code. For example, to allow for a more compact instruction encoding, ARM/Thumb includes an If-Then-Else (ITE ) instruction in THUMB mode that changes up to four consecutive instructions into variants that are conditionally executed based on the value of the status register. Since the approach presented here generates and tests a single instruc-tion at a time, it does not test these cases. Therefore, future work can consider advancing the generation process to iden-tify and generate the necessary instruction sequences to test these variants in the specification. 

# 6 Related Work 

We acknowledge the significant efforts devoted in past stud-ies to test CPU emulators. EmuFuzzer [26] tested x86-64 

CPU emulators using a hardware reference to detect struc-tures within the instruction by observing when mutating a particular byte causes an exception. KEmuFuzz [25] extends EmuFuzzer by adding support for fuzzing virtual machines and hypervisors through carefully crafted templates that in-clude snippets of both user- and system-level instructions, but retained the same instruction generation method as Emu-Fuzzer. The approach is suited for testing x86-64 emulators running in protected mode (32-bit instructions), requires fil-tering branch instructions due to execution environment limi-tations, and only identifies imprecise byte-level structure in instructions. In contrast, PokeEMU [24] generates test in-structions by symbolically executing the emulator’s binary instruction decoding logic. This is similar to the constructor traversal process adopted in GenSYS , but applied to the em-ulator binary. Fast PokeEMU [39] builds on PokeEMU by reducing test case execution overhead by merging multiple instructions into a single test case. In contrast to InSPECtor ,PokeEMU does not generate edge case-triggering input states, as the value of input operands is not used in the decoding logic. Further, InSPECtor ’s objective to guarantee complete constructor coverage implies that the method devised can find bugs in unreachable constructors. Other testing strategies are found in studies examining bi-nary lifters. For instance, MeanDiff [20] compares binary lifters by translating each intermediate representation (IR) into a common IR. Once translated, an SMT solver is em-ployed to check for symbolic equivalence; this circumvents the need to assess the impact of specific input states. How-ever, due to the complexity of the translation process, certain complex instructions are omitted from analysis. In contrast, 

> JuxtaPlayer

, akin to CPU-emulator testing methods, uses a hardware oracle as a reference system and determines equiva-lence by testing carefully selected initial input states, avoiding the need to check the symbolic equivalence of semantically complex instructions, such as floating-point operations. No-19 tably, a prior study analyzed the limitation of Pcode’s formal semantics [27]. This lead to several recommendations to im-prove the Pcode definitions, documentation and resolve bugs in Ghidra. This complements the recommendations resulting from our extensive work across five ISAs to improve SLEIGH 

and the processor specifications in Section 5.1 Alongside these studies, we also acknowledge studies de-veloping techniques to uncovering flaws in hardware-assisted virtual machines [3, 14] or methods to uncover discrepancies in the textual representation of instructions generated by dis-assemblers [29]. Other approaches aim to detect unexpected changes in the processor state of individual hardware CPUs arising from undocumented instructions [11, 23], manufactur-ing defects [33], or hardware implementation issues [33]. In general, similar to our study, these works across sev-eral domains also aim to identify discrepancies. Notably, discrepancies, even one known to differ between hardware implementations, can be exploited by malware for emulator or VM detection, as demonstrated in previous studies [30,34,35]. 

# 7 Conclusion 

This paper introduced a methodology for generating instruc-tions and initial input states that fully explore all machine code sequences decodable by SLEIGH processor specifica-tions. This led to the development of InSPECtor with GenSYS 

and JuxtaPlayer tools. GenSYS is an instruction and state generator used to produce over 1,208,531 test cases across 5 different ISAs, covering all instructions and addressing modes, as well as edge cases. The test cases were used to evaluate the correctness of specifications using a differential testing strategy, realized in JuxtaPlayer . The tool executes each test case in both a 

> SLEIGH

-based emulator and a hardware-based reference sys-tem, followed by a comparison of their final states to identify discrepancies. This process revealed systematic issues in 5  

> SLEIGH

specifications and highlighted areas where improve-ments to SLEIGH specification language could reduce future defects. Improving the veracity of SLEIGH specifications enhances the reliability and confidence in downstream tools that depend on their correctness. Importantly, our work represents a significant and sustained effort to improve SLEIGH specifications and introduces tools and a test strategy for automated correctness testing.

# A Ethical Considerations 

Our work presents a method and tool design for testing and evaluating processor specifications focusing on the open source SLEIGH specifications. Our goal is to improve the truthfulness of the tools used by the security community, such as Ghidra and CPU emulators, that rely on the truthfulness of the SLEIGH specifications, and thereby helping to improve the security of software systems and the safety and security of end-users of those systems. Through our analysis with InSPECtor , we identified a sub-stantial number of defects in existing SLEIGH specifications. While documenting these issues is essential for improving the correctness and reliability of disassembly and analysis frameworks, public discussion of such defects carries some dual-use risks. In particular, an adversarial actor could po-tentially misuse specification inconsistencies to craft binaries that evade static or dynamic analysis, mislead emulators, or otherwise undermine defensive tooling. To mitigate these risks, we followed established responsible-disclosure practices. All defects discovered dur-ing this work were communicated directly to the Ghidra 

project maintainers, together with the corresponding fixes that we validated internally. Our intention is to strengthen the ecosystem of analysis tools rather than expose previously unknown issues without remediation. We emphasize that any future defects uncovered through the use of this tool should likewise be discussed and disclosed responsibly to the main-tainers of the Ghidra project following the guidelines therein. Despite these dual-use concerns, we believe that the bene-fits of improving specification quality, strengthening capabili-ties and correctness of widely used analysis tools—employing those specifications—-used by security practitioners and im-proving transparency outweigh the risks or potential for mis-use. # C Hardware Discrepancies 

x86-64. For x86-64 , we experimented with different hardware reference systems for differential testing, an Intel(R) Xeon(R) CPU E5-2660 v4 CPU and an AMD Ryzen 9 7950X (the CPU used for the final results). However, between the two CPUs, 22 we also identified a large number of discrepancies. Many of these discrepancies are expected. The x86-64 ISA contains several instructions for interacting with model-specific regis-ters or internal processor state (e.g., RDTSC , CLZERO , CPUID )and others for interacting with external hardware ( RDRAND ), all of which yield processor-specific outputs. Additionally, the processors support distinct sets of ISA and vendor-specific additions/extensions, leading to several additional discrepan-cies, partially attributed to the AMD processor being newer than the Intel processor. Expected differences also include instructions that are explicitly listed in the ISA manual (from both vendors) as producing outputs with undefined values. This mostly occurs in arithmetic operations for which certain flags are listed as undefined after the instruction is executed, allowing for more flexibility in the hardware implementation. For example, a considerable number of discrepancies are re-lated to the AMD processor not setting the auxiliary carry flag (AF ), which was originally intended for binary-coded decimal (BCD) operations and is rarely used in modern programs. However, there are also four notable discrepancies that are neither caused by ISA extensions nor explicitly marked as having undefined outputs: 1. Control-flow instructions with an address-size override prefix ( 66 ) are interpreted differently on the two pro-cessors. On the Intel CPU, the prefix is respected and the destination address is truncated to 16 bits, while the AMD CPU ignores the prefix and uses the full 64-bit address. 2. Subtle differences in prefix decoding cause the instruc-tion encoding [f3 47 90] to be decoded as a PAUSE 

instruction on the Intel CPU, but as an XCHG instruction on the AMD CPU. 3. The VGATHER/VPGATHER* family of instructions load values from memory based on an index and a mask reg-ister. Both the index and mask operands are vector reg-isters; however, only the lower 64 bits of the mask are used. The Intel CPU fills the upper bits of the mask register with the value of the most significant bit of the original value, while the AMD CPU leaves the upper bits unchanged. 4. RCPPS and RSQRTPS (and other variants) perform approx-imate reciprocal and reciprocal square root operations respectively using different approximation algorithms on Intel and AMD CPUs, resulting in discrepancies. The issues above that stem from non-standard instruction encodings or input values are highly unlikely to be encoun-tered in real-world programs. Of these issues, only the fourth is likely to impact real-world programs. However, since the associated instructions are explicitly documented as approx-imations, programmers should already be careful when us-ing them. Nonetheless, knowing these discrepancies exist is necessary to accurately assess the correctness of the x86-64 SLEIGH specification. A vast majority of these discrepancies were filtered out during analysis based on their instruction mnemonic to avoid incorrectly attributing them to bugs in the  

> SLEIGH

specification. 

> MSP430

. For some discrepancies between the hardware and  

> SLEIGH

specification, the SLEIGH specification was more faithful to the documentation. For example, the documenta-tion shows the lowest bit of the stack pointer register being fixed to zero and clarifies that it is always even aligned. This gives the impression that bit 0 is hardwired to 0 and that it is not possible to write an odd value to the register. However, the hardware was found to allow and to use odd stack pointer values. This causes data pushed by PUSH.B and PUSH.W to overlap as word memory accesses are forcefully aligned to word boundaries, but byte memory accesses are not. Another behavior that differed between hardware and docu-mentation was the CMPA SR, SR instruction. This instruction should compare the status register with itself and then set the flags based on the result, but was found to interpret the status register in the destination register position as zero. The documentation states that the status register outside of word accesses in the register addressing mode belongs to the con-stant generator. But this is not consistent with the constant generator register as it returns the register addressing mode value of zero in both positions. Issues with constraints in the SLEIGH specification being too relaxed allowed us to find undocumented instructions. The MSP430X extension word is assigned the encoding space from 0x14XX to 0x1CXX, but is defined as only using the encoding of 0x14XX (where XX and the 8th bit are ignored). The constructor in SLEIGH which builds the extension word only checks bits 11–15, and ignores bits 9–10 which should be set to 0. This allowed us to find a special case where the SXTX.W instruction is used with the register addressing mode and bits 8–10 of the extension word set (bit 8 being the zero carry bit). Normally the SXTX.W instruction sign-extends a byte in the destination register to a word size, but this illegal encoding of the instruction sign-extends a word to address size. However, the documentation does not contain this encoding, nor an instruction to sign-extend a word to address size. 

> RISC-V

. The RISC-V SLEIGH specification includes all ex-tensions for a given base instruction set. As the test cases are generated from this there is no way to separate out extensions that are not supported by the hardware being tested. This led to a significant number of illegal instruction exceptions as the hardware could not run the instruction. Another source of illegal instructions was the Control and Status Register exten-sion. These registers are used to control how the hardware functions and to receive status information from the hardware. The SLEIGH implementation of this extension includes ev-ery possible CSR, giving them the generic name of csrXXX where they have not yet been assigned a use. However, the 23 hardware faults with an illegal instruction exception on in-structions that access these CSRs as they are not implemented and have no function. The set of CSRs which can be used for testing is further reduced by the privilege level the hart is running on, as accesses to those on a higher level will also raise an illegal instruction exception. 

# D Pcode Edge Cases 

Below we describe additional details for the edge cases de-fined for individual Pcode operations (Table 1): 

Addition and subtraction. For I NT ADD and I NT SUB , edge cases that test integer overflows/underflows and output values that are negative or zero are potentially interesting. Inputs corresponding to these edge cases are likely to set or clear var-ious CPU flags, testing that the flags are properly updated by the SLEIGH specification, and that the correct set of overflow checks are used. 

Multiplication and division. Since there are both signed and unsigned variants of multiplication and division, edge cases are defined to identify when the incorrect variant is used. It is also useful to include edge cases for division by zero, as the behavior varies across ISAs. 

Zero and sign extension. For these operations, bugs are most likely to result from using the incorrect type of extension. To identify these bugs, edge cases that ensure negative inputs of various bit-widths are used. For example, an input for a 16-bit extension would be 0xFFFF .

Boolean operations. Given that there are only four input combinations for boolean operations, it is possible to test all outputs by constraining the inputs to each of the four combinations. 

Bitwise operations. In SLEIGH , bitwise operations are used for three purposes: implementing ISA-level bitwise opera-tions, extracting and inserting bits, and as an alternative to boolean operations. Misuse of these operations can be de-tected by forcing the inputs to be extreme values (e.g., all bits set to 0 or 1). 

Shifting operations. Overflows are also possible in shift op-erations, and the behavior of oversized shifts varies between ISAs. Edge cases are defined to constrain the shift operand to a value that exceeds the total number of bits in the type. Addi-tional edge cases are defined to test whether the correct type of shift (arithmetic versus logical) is used, by constraining the inputs to be negative or positive values. 

Comparisons. For comparisons, it is desirable to detect cases of off-by-one errors and where the wrong comparison operator is used. To achieve this, constraints are used to enforce that operands are equal or differ by ±1. 

Overflow conditions. SLEIGH explicitly calculates various overflow conditions by using specific operations for each one. Edge cases are defined corresponding to each overflow-checking operation. 

Floating-point operations. For floating-point operations, the operands are constrained to extreme and special values (such as extremely small or large values, NaN, or ±Inf). Floating-point operations are challenging to evaluate symbolically, which prevents us from solving subsequent edge cases that use the result of a floating-point operation. However, within a single instruction, integer and floating-point operations are typically not performed on the same inputs. 

Branches. Branches are handled by forking the symbolic state at each branch operation and adding an assertion for the branch condition. For most branch operations, when the con-dition is true, the operation jumps to a different instruction. However, SLEIGH also allows branches to Pcode operations within the same instruction (internal Pcode branches). For the outgoing edge of external branches, edge case genera-tion stops when the branch is taken, since instructions are individually tested. Internal loops (where the branch jumps backwards within the instruction) are handled by unrolling the loop a fixed number of times (e.g., 10) and generating edge cases for each unrolled iteration. 

Memory accesses. When a value is loaded from memory, it may be used as an input to subsequent operations. To generate edge case-triggering operands for these operations, memory is included as part of the initial input state. Whenever a load occurs, the state generator introduces a new symbolic input variable representing the value returned from the load and records the expression for the address from which the value is loaded. Since not all addresses are valid for every architecture, additional constraints are used to restrict the addresses to valid ranges and, for some architectures, to ensure that the address is properly aligned for the access size. Constraints are also added to ensure memory accesses are consistent, so that multiple loads from the same address return the same value. For stores, the same constraints are applied to the address (to prevent invalid access exceptions from occurring), but the written value is ignored. It is technically possible for the value written by a store to be later loaded; however, there are no instructions in any of the tested ISAs where this occurs, so it can be ignored for the purpose of state generation.

AArch64 STRLB/STRLH. These instructions store abyte/half-word to memory. AArch64 LD2R/LD3R/LD4R. These instructions load mul-tiple values from memory, and store repeating copies of each value into different SIMD registers. However, the SLEIGH

> JuxtaPlayer

# F.2 KVM-based Reference Systems 

Since our goal is to ensure that SLEIGH specifications accu-rately reflect the behavior of real hardware, we use real hard-ware as the reference system for differential testing. Where possible, hardware-assisted virtual machines (VMs) are used to support this goal. These VMs create isolated virtual exe-cution environments that can be used to efficiently execute instructions on the underlying hardware. By carefully config-uring the VM state, it is possible to construct an environment analogous to that of the emulator. Hardware virtualization differs between ISAs and even between different vendors of the same ISA. 14 Fortunately, the Linux kernel provides a hardware virtualization driver, KVM (Kernel-based Virtual Machine), which exposes a consistent interface for manipulating hardware VMs. KVM supports all the essential features for differential testing, allowing us to read and write register values, allocate memory, and single-step the processor. However, some additional configuration is required to en-sure that the VM environment matches the assumptions made by the SLEIGH specification. This configuration is performed by JuxtaPlayer using KVM APIs, below we describe the x86-64 specific configuration steps; the ARM/Thumb and AArch64 

configurations requires similar steps.  

> x86-64

processors support multiple execution modes (e.g., real mode, protected mode, and long mode), each of which can change the semantics of a particular instruction encoding. Therefore, hardware VMs must be configured to run in the correct mode (i.e., long mode for x86-64 ). To do this, the relevant bits in control registers, such as EFER (Extended Feature Enable Register), are set to enable ISA extensions related to long mode execution, and the global descriptor table (GDT) is set up to ensure that the memory region containing the instruction bytes is interpreted as 64-bit code. To ensure all instructions are available, JuxtaPlayer enables additional extensions, such as SSE and AVX, by setting bits 

> 14 Intel CPUs implement a set of virtualization extensions called VT-x, while AMD CPUs implement a different set of extensions called AMD-V (or SVM—Secure Virtual Machine).

25 in the appropriate control registers and configuring the VM’s 

CPUID . To handle memory accesses, JuxtaPlayer also con-figures the page table, a hierarchical data structure used for hardware address translation, to map the instruction page and any additional memory from the test case’s initial input state. The final challenge is to support single-stepping in the VM execution environment. On both the Intel and AMD CPUs, single-stepping is implemented by setting the trap flag (TF), which causes a debug exception after each instruction return-ing control to the hypervisor, which in turn returns control to 

> JuxtaPlayer

. KVM automatically handles this process, mak-ing it straightforward to single-step instructions in most cases. However, this debug exception can be suppressed by higher priority exceptions (e.g., memory violations) that occur during instruction execution. If such an exception occurs, control is not returned to the hypervisor; instead, the processor executes the corresponding exception handler. If no handler is present, a ‘triple fault’ occurs, resetting the VM and losing the state needed for differential analysis. To prevent this, JuxtaPlayer 

defines exception handlers that immediately exit back to the hypervisor. The VM is configured to use these handlers by setting the appropriate entries in the interrupt descriptor table (IDT), updating the task state segment (TSS), and mapping memory for the exception stack. When exceptions occur, we recover the exception reason using a combination of the RIP (instruction pointer) and CR3 (faulting address) registers. 

# F.3 Hardware Reference Systems 

For MSP430 and RISC-V , we did not have access to hardware that supported hardware virtualization extensions, making it impossible to use KVM-based VMs for differential testing. In these cases, alternative approaches where required to execute instructions on real hardware while still allowing the system state to be manipulated and observed. These alternative ap-proaches are generally less efficient and robust than hardware virtualization, but since the ISAs in question are typically simpler they suffice for differential testing. As the reference system for MSP430 , we use aMSP430FR5969 microcontroller which contains an EEM (Energy-Efficient Microcontroller Emulator) module that can single-step instructions and read/write the system state. This microcontroller used disjointed memory regions for code, ram, MMIO peripherals, and other functions, with the gaps either trapping on access or allowing reads with a constant value. To keep the test environment consistent, breakpoints were used to detect memory accesses outside of the generic mem-ory ranges, as no form of memory protection was available. However only 2 breakpoints could be enabled at once and no resulting information from the breakpoint was reported. This required nops to be inserted after the instruction under test for different trapping addresses, and each test case to be repeat multiple times in a greater/less than scan. The lack of any form of memory protection also allowed the possibility of an instruction writing an unknown value to any MMIO reg-ister, requiring the microcontroller to be fully reset between testcases to ensure a clean state. For RISC-V we use the BeagleV®-Ahead containing a quad-core Xuantie C910 processor which implements RV64GC including the 0.7.1 draft version of the vector ex-tension. This board is capable of running Linux however lacks support for KVM. Instead ptrace was used to seize control of a newly created process as an isolated execution environment. The required memory regions would then be mapped into the process, and the initial regions unmapped. To account for ptrace’s missing support for single stepping, the test cases were first executed with memory filled with 

c.ebreak instructions to detect jumps. Instructions without jumps were re-executed with memory populated with the test-case specified values. RISC-V jump instructions do not load from memory, allowing the execution with incorrect memory values to be used as the final result.

## 摘要
形式化规格提供了强有力的保证，但手动编写成本仍然很高。近期基于大型语言模型的方法通过从源代码中推断规格来实现自动化，但其对白盒访问的依赖因知识产权风险和部署成本而阻碍了工业应用。我们的方法使用大型语言模型仅从测试代码和动态执行轨迹中推断候选规格：大型语言模型只观察程序接口、所选输入及相应的输出或状态变化，而实现内部细节保持隐藏。候选规格使用有界模型检查在本地验证，反馈信息用于指导迭代改进。在SpecGenBench基准上的初步结果表明，测试可以引导大型语言模型生成有意义的Java建模语言规格，同时也揭示了检查器兼容性和诊断反馈是可靠改进的关键挑战。

## Abstract
Formal specifications offer strong guarantees, but remain costly to write manually. Recent LLM-based approaches automate this by inferring specifications from source code, yet their reliance on white-box access poses barriers to industrial adoption due to intellectual property risks and deployment costs. Our approach uses LLMs to infer candidate specifications solely from test code and dynamic execution traces: the LLM observes only the program interface, selected inputs, and corresponding outputs or state changes, while the implementation internals remain hidden. Candidate specifications are validated locally using bounded model checking, with feedback guiding iterative refinement. Initial results on the SpecGenBench benchmark suggest that tests can guide LLMs towards meaningful Java Modeling Language specifications, while also highlighting checker compatibility and diagnostic feedback as key challenges for reliable refinement.

- **核心思想**：将程序作为黑盒呈现给 LLM，仅提供接口、测试代码和结构化执行观察；候选规格用本地有界模型检查（BMC）验证，反例反馈迭代细化。

  2. **LLM 规格推断**：
     - 使用零样本提示（zero-shot），输入：方法签名、调用该方法的测试代码、对应的观察轨迹。

  3. **规格验证与细化**：
     - **一致性检查**：用 BMC（工具：JJBMC）在给定界限内检查实现是否可能违反候选规格；若违反则返回反例，作为新观察反馈给 LLM。

## 6. 论文的主要结论与发现

- **可行性证据**：在无源码头访问条件下，LLM 确实可以从测试代码 + 执行观察生成有意义的 JML 规格；22 个任务中 11 个成功通过验证（其中 7 个首轮即通过，4 个经细化通过）。
- **观察补充测试断言**：测试本身可能只断言部分行为，但观察轨迹能暴露额外状态变化（如 balance 之外的 checksum 更新），使规格能捕获测试未直接验证的行为。
- **关键挑战**：
  - **检查器兼容性**是最大瓶颈：9 个任务因生成的 JML 超出 JJBMC 支持子集（如 `\num_of`、ghost/model 字段、量化变量上的算术表达式）而中断，属于工具链问题而非语义错误。
  - **诊断反馈不足**：2 个 Fail 任务因 JJBMC 只返回“断言失败”并给空反例，LLM 无法获得可操作的修正确据。
  - **BMC 界限**影响验证精度，是已知问题。

## 7. 优点

- **隐私友好的设置**：LLM 只接触接口、测试、处理后观察，不接触实现内部，特别适合中小企业和保密性要求高的场景。
- **结合两种证据**：同时利用测试代码中的 oracle 信息和执行观察中的动态状态转换，比单纯用测试代码或单纯用执行轨迹信息更充分。
- **反例引导迭代闭环**：不仅生成规格，还用 BMC 验证，并将失败信息反馈给 LLM，形成“生成—验证—修正”的机制。
- **区分“验证通过”与“真正完全正确”**：论文明确说明通过检查只是“已验证候选”，不保证完全规格，态度严谨。
- **实现细节丰富**：观察格式（`args/pre/post/outcome`）、两阶段提示规则、双检查设计（一致性 + 覆盖）都有清晰描述，易于复现。

## 8. 不足与局限

- **工具链碎片化**：JJBMC 仅支持 JML 子集，限制了大模型表达力；Error 占 40% 以上，说明“可验证”比“可生成”更难。
- **反例质量差**：BMC 失败时缺乏具体反例，使迭代细化退化为猜谜，严重影响自动化率。
- **实验规模小且无对比**：22 个任务规模有限，缺少与白盒 LLM 方法、Daikon 等传统方法的质量对比。
- **数据泄露风险**：SpecGenBench 可能已进入 LLM 预训练数据，削弱评估可信性；作者计划未来用私有工业数据缓解。
- **未测动态复杂特性**：排除了字符串、堆可达性等场景，限制了结论适用范围。
- **未报告算力和成本**：LLM API 调用次数、时间消耗等缺失，难以评估工业部署经济性。

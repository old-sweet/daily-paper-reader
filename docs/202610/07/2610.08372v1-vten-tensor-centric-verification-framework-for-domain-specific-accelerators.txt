## Abstract 

The semantic gap between tensor-centric software models and signal-level hardware testbenches creates significant productiv-ity bottlenecks in verifying Domain-Specific Accelerators (DSAs). Existing frameworks like Cocotb suffer from prohibitive synchro-nization overheads due to fine-grained interactions. To address this, we propose vTen, a data-centric framework that strictly decou-ples verification intent from execution mechanics. By leveraging a declarative DSL and kernel-granular batching, vTen minimizes host-simulator interaction frequency. Evaluation on a production-scale 3D U-Net accelerator demonstrates that vTen achieves a 2 × perfor-mance improvement in simulation latency and a 60.3% reduction in code complexity compared to Cocotb.

## 1 Introduction 

Deep learning models have been widely adopted for various tasks such as image classification [8], object detection [18], and image segmentation [19]. The rapid popularity of diverse AI models is driving the development of domain-specific accelerators across academia [9, 14–16, 22] and industry [7, 11]. This workload diver-sity has driven the proliferation of domain-specific accelerators (DSAs) across the entire design stack—from RTL simulation and SoC integration to FPGA prototyping and ASIC tape-out. As a result, verification — the process of validating the correctness of hardware modules (e.g., register-transfer level (RTL) designs or FPGA im-plementation) against golden software workloads (e.g., written in PyTorch [17] or TensorFlow [2]) — appears as an emerging chal-lenge in hardware design development. Industry surveys report that verification consumes 60–70% of design effort [6]. The growing complexity of integrated circuits has intensified the challenges in hardware design verification. ## 2 Background and Motivation 2.1 AI Domain-Specific Accelerators 

Modern deep learning models typically consist of general matrix multiplication (GEMM) operations (e.g., convolution or fully con-nected layers) and non-GEMM operations, such as memory opera-tions, normalization, and logit computation. Among them, GEMM operations are still dominant in terms of the number of operations and overall latency, ranging from 42.8% to 96.6% [12], and have been the prime optimization targets for domain-specific accelerators. The fundamental computing pattern of GEMM operations is the large use of basic operations such as multiplication and accumulation (MAC), which can be accelerated by massive parallel processing elements (PEs) [7, 9, 11, 14–16, 22]. To leverage highly parallel PEs, it is essential to consider massive data movements across various memory levels, including HBM or DRAM, cache or global memory, and registers [11, 14, 16]. For example, to execute a convolution layer, a DSA transfers weights and input feature maps (IFMs) from an external memory to a global on-chip buffer. In a DSA, data is moved between buffers and a PE array via a standard bus interface, such as AXI. The output results (so-called output feature maps (OFMs)) can be stored in on-chip memory or transferred to external memory via a direct memory access (DMA) module. In short, designing an AI accelerator requires managing massive data movements across different modules.

## 2.3 Challenges for DSA Verification 

DSA verification presents a unique challenge for existing method-ologies such as UVM [1] and Cocotb [20]. As explained in Section 1, there exists a fundamental semantic gap between data-centric test-benches and control-centric hardware simulation during verifica-tion. The gap can be intensified when verifying hardware modules in a DSA design. The challenges can be described as follows. 

Challenge 1 (Massive Repetitive Operations) : To validate the functional correctness of a module in a DSA, it is generally neces-sary to conduct a simulation with large-scale tensors, for example, weights or IFMs of multiple convolution layers. As a result, it may impose considerable burdens on hardware designers when adopt-ing UVM [1] for simulation/verification of large-scale tensors. For example, as illustrated in Figure 2(a), with UVM, the driving loop is offloaded to SystemVerilog. However, it requires complex cross-language data transfer, such as uvm_conn.send(packed_data) .Meanwhile, from a control-centric simulation perspective, the flow is highly repetitive, consisting of a set of predefined operations. Here, as demonstrated in Figure 2(b), with Cocotb, the iteration occurs in the Python runtime ( for word in packed_data ). Con-sequently, every single data beat triggers multiple VPI operations: writing values ( dut.tdata.value ), scheduling callbacks ( await RisingEdge ), and reading status ( dut.tready ). For DNN work-loads involving millions of cycles, this chatter between Python and the backend process creates a prohibitive performance bottleneck. 

Challenge 2 (System Integration) : Designing a DSA also in-volves integrating and validating multiple block designs, including vTen: Tensor-Centric Verification Framework for Domain-Specific Accelerators DAC ’26, July 26–29, 2026, Long Beach, CA, USA

These observations pose a strong demand to design an alternative verification framework. A target design must effectively bridge the semantic gap between tensors and hardware simulation. It is also essential to achieve scalable performance for data-intensive workloads while achieving portability for design reuse and system integration. 

## 3 vTen Architecture 3.1 Methodology and Architecture Overview 

Methodology. vTen bridges the semantic gap and mitigates syn-chronization overheads via a tensor-centric approach, prioritizing throughput without sacrificing flexibility for diverse DSAs. The design rests on three fundamental principles: (1) Data-Centric Ab-straction — decouples verification intent from execution mechanics by elevating the specification level from pin-level transactions to operations on tensors and registers; (2) Kernel-Granular Execution 

— treats the Kernel —defined as the accelerator’s top-level DUT en-compassing compute logic and interfaces— as the atomic unit of interaction. By batching tensor operations into a single execution unit, it reduces host-simulator synchronization frequency from 

𝑂 (𝐶 ) to 𝑂 (1), where 𝐶 denotes the kernel execution cycles; (3) 

Shared Memory Data Plane — utilizes serialized byte streams to enable direct backend access, bypassing the high-latency IPC over-head inherent in transaction-level interfaces. 

Architecture. Following the design methodology, vTen introduces a layered architecture, as illustrated in Figure 3. Instead of a mono-lithic testbench, the framework decouples verification into three distinct layers, effectively separating high-level intent from low-level execution mechanics. First, at the Frontend or Intent layer ,users define verification intent using a Python-based DSL. This layer focuses purely on dataflow, abstracting away cycle-level tim-ing and physical port protocol. Second, at the Runtime or Ab-straction layer , the runtime engine leverages Kernel Abstraction definitions to automatically lower high-level DSL operations into a backend-agnostic Execution Intermediate Representation (Execu-tion IR) while handling tensor serialization and address mapping. Third, at the Backend or Execution layer , a split-process execu-tion engine executes the compiled Execution IR batches. By utilizing shared memory and batch execution, the backend maximizes simu-lation throughput while reducing host-simulator transactions.

## 3.2 Domain-Specific Language for Data-Centric Verification 

3.2.1 Core Abstractions. The DSL serves as the declarative fron-tend interface, enabling users to define verification intent through high-level dataflow rather than low-level signaling. It provides a set of hardware-agnostic primitives that act as abstract templates for data movement (e.g., write_tensor , read_register ) and logical synchronization (e.g., barrier ). By abstracting away specific trans-port mechanisms (e.g., AXI4-Stream vs. AXI4-MM), these primitives strictly decouple the verification logic from interface implemen-tation details. This allows the testbench to focus solely on the tensor-level dataflow intent, leaving the Runtime to automatically bind these abstract operations to the specific hardware protocols via Kernel Abstraction (Section 3.3).

## 3.3 Bridging the Semantic Gap: Kernel Abstraction 

To bridge the semantic gap, the Kernel Abstraction layer provides the necessary mapping intelligence to drive physical hardware ports from high-level tensor specifications. It automates the lowering of DSL operations into address-aware Execution IR and manages the data serialization/deserialization processes, thereby decoupling verification logic from architectural details. This abstraction is ma-terialized through a two-phase lifecycle: 

3.3.1 Build-time Kernel Template. The Kernel Template serves as a static, parameterizable blueprint of the Kernel. It is constructed by extracting interface specifications from lightweight RTL pragmas and retrieving tensor/register definitions from the Python-based functional reference model. Architectural attributes—including ten-sor shapes, register reset values, and protocol parameters—can remain parameterized at this stage. This separation allows verifica-tion logic to remain agnostic to specific architectural tuning (e.g., changing array sizes or bus widths).

The shared memory transport model (detailed in Section 3.4) maps naturally to PCIe DMA, allowing future backends to ex-ecute the same instructions on FPGAs, ensuring test portability across the verification lifecycle. 

## 3.4 Scalable Execution Layer 

We leverage the Backend Execution Engine (Figure 3) to implement a scalable execution strategy. This architecture is designed around vTen: Tensor-Centric Verification Framework for Domain-Specific Accelerators DAC ’26, July 26–29, 2026, Long Beach, CA, USA 

two core principles: minimizing runtime overhead through build-time code generation and eliminating synchronization bottlenecks via decoupled data/control transport planes. 

3.4.1 Lightweight Runtime Architecture. To ensure the Backend Interface operates with minimal latency, vTen enforces a strict sep-aration between static definition and dynamic execution. Computa-tionally expensive tasks such as interface parsing and BFM code generation are offloaded to the Build-Time phase. Consequently, the 

Runtime execution loop becomes extremely lightweight, handling only 𝑂 (1) Binding Table lookups and dispatching pre-compiled Execution IR. This design eliminates recompilation overhead, facil-itating rapid iterative testing on the target hardware. 

3.4.2 Split-Process Execution Model. To overcome the synchro-nization bottlenecks identified in Section 2, vTen redefines the abstraction boundary between the host and the backend. Instead of tight cycle-level coupling, we decouple execution into two distinct planes: a Data plane and a Control plane. 

Data Plane: Shared Memory Transport. Serialized tensors are pre-populated into a shared memory data plane prior to kernel execution. This design isolates data transport costs from simulation logic and enables direct backend access without IPC serialization overhead. Crucially, this transport is backend-agnostic; the backend can retrieve data either via direct pointer access (for C++ environ-ments) or via DPI calls (for SystemVerilog simulators). This direct access capability allows vTen to approach the theoretical perfor-mance limit of native C++ testbenches. 

Control Plane: Kernel-Granular Batch Execution. The control plane amortizes IPC latency through Kernel-Granular Batching. A Kernel Task encapsulates a complete execution unit: the target kernel instance, and the compiled Execution IR sequence. The host submits this atomic batch to the backend and the synchronization is managed via a simple lightweight handshake (Host start ↔

Backend complete ). This mechanism reduces the interaction over-head from linear with cycles ( 𝑂 (𝐶 )) to constant per kernel launch 

𝑂 (1), preserving cycle-level debugging capability via BFMs.

## 4 Evaluation 4.1 Experimental Setup 

Design Under Test (DUT). We evaluate the performance of vTen against Cocotb on a custom NPU shown in Figure 6 for 3D segmen-tation models such as 3D U-Net [24]. Such a complicated DUT is chosen to analyze Cocotb’s overall VPI overhead associated with system integration of multiple submodule layers. The architecture comprises distributed IPs linked via AXI4-Stream, utilizing AXI4-Lite for configuration and AXI4 for tensor access (IFMs, Weights, OFMs). These interfaces connect to vTen or Cocotb BFMs during simulation. The design demonstrates production-scale complexity, utilizing 1,802 DSPs and 385 URAM blocks when synthesized on a Xilinx Alveo U280 FPGA at 125 MHz. 

Workloads. We select Conv3D layers (kernel=3, stride=1) for work-load evaluation, as their large tensor footprints heavily utilize the DUT’s interface bandwidth. We evaluate multiple test cases with increasing tensor sizes and NPU cycle counts, starting from 

(𝐶, 𝐷, 𝐻,𝑊 ) = (32 , 4, 4, 4) and doubling dimensions, to monitor overheads with diverse VPI count and payload sizes.

## 4.3 End-to-End Performance Analysis 

This experiment evaluates the end-to-end performance on the 3D U-Net case study defined in Section 4.1. Figure 8(a) shows that vTen achieves a 2 × speedup in Test Execution ( 𝑇 𝑒𝑥𝑒𝑐 ) compared to Cocotb across workloads ranging from 1K to 64K NPU cycles. Since the DUT execution itself is identical, this gain is attributed entirely to the elimination of VPI-induced context switching required for clock advancement. In Cocotb, the Python interpreter must wake up every cycle to drive the clock and signals, creating a dominant overhead that scales with simulation time ( 𝑂 (𝐶 )). vTen removes this bottleneck by offloading clock generation and batched transac-tions to the backend. This architectural shift effectively neutralizes the cumulative latency incurred by massive repetitive operations (Challenge 1). While Figure 8(b) indicates higher loading latency ( 𝑇 𝑙𝑜𝑎𝑑 ) for vTen, this results from front-loading data transfer to Shared Mem-ory, whereas Cocotb defers signal driving to the execution phase. This one-time setup effectively decouples transport from execution, enabling the performance gains demonstrated in Figure 8(a). Cru-cially, this upfront cost remains negligible (<1% of total latency), ensuring that transport does not bottleneck the overall simulation. 

## 4.4 Verification Productivity Analysis 

Addressing Challenge 2 (System Integration) with heterogeneous IPs (e.g., DMA, MAC), vTen achieves a 92.2% reduction in verification-specific code (28 vs. 360 lines). By encapsulating golden references within Kernel Objects, vTen facilitates hierarchical composition, al-lowing users to simply aggregate existing unit specifications instead of rewriting top-level logic. Consequently, this approach eliminates 242 lines of manual serialization and AXI4 sequencing required in Cocotb. Including the shared golden model, vTen demonstrates a 60.3% overall reduction (261 vs. 658 lines), proving that Kernel Abstraction resolves integration bottlenecks via modular reuse. 

## 5 Related Work 

Existing hardware verification frameworks follow three approaches. Simulation acceleration includes hardware-based solutions (Fire-Sim[13], DiffTest-H[23], ASH[5]) that leverage FPGA/emulator plat-forms for faster simulation, and software optimizations (Verilua[4]) that improve simulator performance. Design-verification languages (Chisel[3], PyMTL3[10]) integrate verification capabilities directly into hardware construction languages, enabling unified design and test flows. Portable verification frameworks (cocotb[20], fault[21]) provide language-agnostic interfaces for test reuse across differ-ent simulators and formal tools. However, these approaches face fundamental limitations: hardware acceleration is primarily suited for SoC-level verification with significant setup overhead, design-specific languages create fragmented toolchains, and portable frame-works sacrifice performance for abstraction. These limitations are particularly acute for AI accelerator verification, which requires handling massive tensor datasets and complex data serialization— motivating vTen’s compiled verification paradigm that eliminates per-transaction overhead while enhancing verification productivity. 

## 6 Conclusion 

In this paper, we propose vTen, a data-centric verification frame-work designed to bridge the semantic gap in Domain-Specific Ac-celerator (DSA) verification. By decoupling verification intent from execution mechanics through declarative DSL and kernel-granular batching, vTen effectively eliminates the synchronization bottle-necks found in traditional methodologies. Evaluation on a 3D U-Net accelerator demonstrates that vTen achieves a 2x performance improvement in test execution and a 60.3% reduction in code com-plexity compared to Cocotb[20]. These evaluation results highlight vTen’s capability to provide a scalable, backend-agnostic verifica-tion solution, lowering entry barriers and accelerating agile devel-opment for next-generation AI hardware.

## 摘要
MachCSL是一个用于在基于Sail RISC-V语义的RISC-V计算机底层语义之上验证系统软件（如操作系统内核）的框架。MachCSL的关键思想是调整基于Iris的并发分离逻辑，使其能够推理亚指令级别的底层硬件执行：页表转换、TLB、特权级别、配置寄存器、指令取指/译码/执行、陷阱与中断、DMA、共享内存、电源故障等。在此细节层面进行推理可确保系统软件正确管理所有硬件细节。在如此低的抽象层次上验证软件是繁琐的，但基于LLM的智能体能够推理此类底层细节。作为案例研究，我们验证了xv6操作系统内核（6,593行C和汇编代码），该内核提供了传统的Unix系统调用接口（进程、文件系统、文件描述符和抢占式调度），并具有大量内部并发（多核支持、细粒度锁、共享内存、中断、DMA等）。在验证过程中，我们发现了xv6实现中的九个错误，以及Sail RISC-V语义中的一个错误。验证工作耗时77天，包括开发MachCSL框架的时间。

## Abstract
MachCSL is a framework for verifying systems software, such as an OS kernel, on top of low-level semantics of a RISC-V computer, based on the Sail RISC-V semantics. The key idea behind MachCSL is to adapt concurrent separation logic, based on Iris, to reasoning about low-level hardware execution at the sub-instruction level: page-table translation, TLB, privilege levels, configuration registers, instruction fetch/decode/execute, traps and interrupts, DMA, shared memory, power failures, etc. Reasoning at this level of detail ensures that the system software correctly manages all of the hardware details.   Verifying software at this low level of abstraction is tedious, but LLM-based agents are capable of reasoning about such low-level details. As a case study, we verify the xv6 OS kernel (6,593 lines of C and assembly code), which provides a traditional Unix system call interface (processes, file system, file descriptors, and preemptive scheduling) and has substantial internal concurrency (multi-core support with fine-grained locking, shared memory, interrupts, DMA, etc.). In the verification process, we uncovered nine bugs in the xv6 implementation, as well as one bug in the Sail RISC-V semantics. The verification effort took us 77 days, including the time to develop the MachCSL framework.

- **核心问题**：操作系统内核的正确性直接关系到所有应用的安全，但内核必须管理极其复杂的底层硬件细节（页表翻译、TLB、特权级、配置寄存器、指令取指/译码/执行、陷阱与中断、DMA、共享内存、电源故障等），同时还要处理大量并发（多核、异步中断、硬件页表遍历与内核并发访问、DMA、系统崩溃重启等）。
- **已有工作的不足**：先前的内核验证工作（如 seL4、CertiKOS、Hyperkernel 等）多在 C、Rust、LLVM IR 或理想化汇编层面进行验证，抽象掉了硬件的页表遍历器、TLB、精确陷阱/中断语义、内存访问设备等细节；且多数内核是专门为验证而设计或重写的。
- **本文的目标**：验证一个**现有**的、真实的、类 Unix 的教学内核 xv6（6,593 行 C 和汇编），且验证建立在 **RISC-V 硬件低层语义级别**（基于 RISC-V International 的 Sail RISC-V 模型），实现"整个系统定理"，即对最终的 ELF 二进制和磁盘镜像的每一次执行均保持内核不变量。
- **整体意义**：证明了将并发分离逻辑（CSL/Iris）扩展到**亚指令级硬件语义**的可行性，也首次证明 **LLM 智能体能够胜任这种极其繁琐的低层系统验证任务**，为操作系统内核的形式化验证提供了新范式。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 整体框架 MachCSL

- 以 **Sail RISC-V 正式语义**作为硬件基础（通过 Sail 的 Rocq 后端翻译为 Rocq 中的单子编码），并自行构建共享内存（TSO 语义）、UART、DMA 磁盘控制器、PLIC 中断控制器、电源故障/重启等模型。
- 实现细粒度交错：可以在**单个内存读/写事件级别**、**寄存器读写级别**交错多个 HART、设备和中断，精确捕获硬件页表遍历与内核更新页表竞争、写缓冲导致的 TSO 弱内存行为等并发场景。
- 使用 **Iris/CSL** 作为核心推理框架。所有规范都是针对机器码（汇编指令序列），从而把编译器、汇编器、链接器完全排除在 TCB 之外（验证的是编译出的二进制）。

### 2.2 CSL 的核心概念与方法

- **资源所有权**：以 `a ↦ Mem v` 表示某内存地址的唯一所有权；以 `r ↦Reg v` 表示寄存器所有权。并发线程间通过资源分割实现独立推理（类似 Rust 的所有权/借用思想）。
- **持续性资源**：只读/不可变状态可转换为 persistent 事实，由多个线程共享。
- **不变量（invariants）**：多线程共同访问的共享内存（如自旋锁的锁字）不能由单线程独占，通过不变量表示，在原子指令执行时通过 `̇ |⇛`（update modality/fancy update）回调机制临时打开、关闭。
- **指令规范**：每个指令都有首条/后续状态的规范。例如 `AMOSWAP` 的规范精确描述了在打开锁不变量瞬间对于旧值（0/1）的处理逻辑，并携带资源 `Q` 将锁内资源（如 `P`）传递给新持有者。
- **CPU 无限循环的 WP（weakest precondition）抽象**：`wp CpuLoop` 表示"从当前状态可以安全地永远执行 CPU 循环"。由于没有函数/返回概念（只有 PC、中断跳转等），规范以**续延（continuation）**形式表达：被调用者证明自己这段代码安全，同时由调用者证明返回到 `ra` 之后继续安全执行。

### 2.3 关键子系统建模和证明要点

- **中断处理**：`sie_cap_gpr` 资源统一管理中断使能状态、栈剩余空间预算、寄存器集合（用 `m` 抽象表示，以支持线程跨核迁移）、trap handler 地址（stvec），允许在指令边界对任意数量的中断进行归纳推理。
- **页表与 TLB**：`strans_inv` 拥有 satp、tlb 和页表物理页，用 ghost state 维护逻辑映射；处理了硬件 A/D 位写回与其他核心改页表之间的竞争。
- **引导阶段的翻译层级**：用"translation tier"概念统一引导早期恒等映射与后期内核页表映射的单调增长。
- **上下文切换**：`valid_context` 将"恢复现场后能安全继续执行"的 `wp CpuLoop` 存入 context 结构；`swtch` 的规范支持线程在不同 HART 上恢复。
- **自旋锁**：与中断禁用耦合（push_off/pop_off）、持有锁集合/加锁顺序约束以避免死锁、支持动态分配的可取消锁不变量（如 pipe 锁）、以及 sleeplock 的特殊规范。
- **TSO 弱内存模型**：引入**视图（view）**概念处理核心间资源移动；细粒度资源 `a ↦𝜉 {S}` 表示在视角 𝜉 下读取地址 a 可返回集合 S 中的任意值；提出**挂起视图（suspended views）**以支持线程跨核调度。
- **文件系统崩溃一致性**：区分持久的磁盘状态 `D` 与内存状态 `M`，证明日志提交后 `D=M` 且保持一致性；通过"写许可（write permit）"回调将扇区持久化的时刻和 crash invariant 关联起来。
- **进程退出与栈回收**：规范使用分离逻辑的 `∧` 操作符，调用者可为"永不返回"的函数（如 sys_exit）提供 `stack_reclaim` 资源以回收整个内核栈。
- **用户态验证**：证明 `user_inv`——从任意 PC 以用户态执行任意代码循环；唯一出口是陷入内核 trap handler（`user_trap_frame`）。发现 user 态可执行 WRS.NTO 休眠指令，需放宽"核心必须活跃"假设。

## 6. 论文的主要结论与发现

### 6.1 验证结论

- 整个 xv6 内核（上游真实内核、非为验证而设计）已验证通过机器检查的顶层整系统定理，可推出：
  1. 内核完整性（无断言失败、无双释放、无任意跳转）
  2. 进程隔离（任意用户代码无法破坏内核）
  3. 崩溃安全性（磁盘文件系统在断电等任意并发下保持一致）
  4. 硬件安全（不会触发未定义的硬件行为）
- 证明了 LLM agent 主导的低级硬件验证路径能够大规模落地。人工只需提出抽象/设计裁决，大量繁琐证明由 agent 生成并由 Rocq 机器检查。

### 6.2 发现的具体 Bug（共 10 个）

| Bug | 组件 | 后果 |
|---|---|---|
| A/D 写回是盲目写 | Sail 模型 | 一个 CPU 能"复活"另一个 CPU 已清除的页表项 |
| iput 回收 struct inode 而非 inode 号 | 文件系统 | 并发的 iput/ialloc 导致磁盘 inode 孤立到下次重启 |
| 在断开链接的目录中创建文件 | 文件系统 | 指向空闲 inode，内核因类型非 T_DIR 而 panic |
| nlink 溢出 | 文件系统 | nlink 溢出后 unlink 导致 panic |
| 调度器未重置 push_off 计数 | 调度器 | 调度器重开中断，扫描进程表和 WFI 之间可能错过唤醒 |
| 部分 writei 未记日志 | 文件系统 | 部分写块从未写入日志，缓存回收后读回旧数据 |
| 用户代码执行缺失 icache fence | exec/跳板 | 陈旧 icache 条目可被新进程执行 |
| freeproc 更新 p->parent 未持有 wait_lock | 进程 | 写入未受锁保护 |
| UART TX FIFO 处理不一致 | UART | printk 与控制台写竞争时溢出 TX FIFO |
| 引导代码未启用 ADUE | 引导 | 规范硬件上内核收到 A/D 陷阱但未处理 |

### 6.3 对 LLM 智能体工作方式的经验

- Agents 的主要弱点是不能引入新抽象、不擅长推理并发；但它们非常擅长在给定清晰的分离逻辑规范和不变量下编写形式化证明。
- 多 agent 设计评审（多个 agent 互相审视设计文档），以及"从全新上下文开始"的工作方式可有效跳出 agent 无限循环、清除隐含错误假设。
- 严格的按函数拆分（SpecF.v/CodeF.v/ProofF.v/LinkF.v）文件组织方式保证了 proof 可以并行构建，并显著降低 agent 混淆的可能性。

## 7. 优点：方法或实验设计上的亮点

1. **真硬件级底层语义与全系统范围**：验证直接在 Sail RISC-V 亚指令级语义之上进行，包含了硬件页表遍历、TLB、特权级、中断、DMA 等。这使得如 A/D 位写回、trampoline 页表切换窗口安全、物理内存耗尽导致的不可达 panic 等深层次特性都被证明覆盖。
2. **TCB 小且干净**：编译器、汇编器、链接器、mkfs 均不在 TCB 内；通过 Print Assumptions 确认顶层定理只依赖少量已知合逻辑公理。
3. **CSL 的模块化与并发能力**：Iris 的本地推理能力让大部分证明无需显式枚举所有并发交错；对锁、不变量、幽灵状态的运用可系统化处理真实内核中的高度并发。
4. **Bug 发现能力**：发现了一批非常隐蔽的实际 bug（如部分写未记日志、iput 竞争、ADUE 缺失、icache fence 缺失），充分说明该验证级别的必要性和有效性。
5. **模型验证并重**：不仅验证了内核代码，还通过 QEMU/真实开发板的 conformance testing 交叉验证了模型本身，修复了多个设备模型的差异。
6. **对 AI agent 的新型应用**：对 agent 的开发工作量、token 用量、失败模式进行了详细记录，展示了 agent 辅助证明的低成本和可扩展性（77 天完成 1.3M 行 Rocq；每个内核改动约 35 分钟即可自动修复全部 proof）。

## 8. 不足与局限

1. **安全性而非活性**：论文只证明了安全属性（如不 crash、不变量保持），**未证明活性属性**（如每个进程最终都能获得调度、无死锁）。锁排序规范仅是"实践中消除死锁"，并未形式化证明无死锁。
2. **无非干扰性质**：不涉及进程间的信息泄露/机密性等非干扰安全性质。
3. **TCB 假设依旧存在**：Sail RISC-V 模型、Rocq 证明检查器、ELF 转储工具以及自行扩展的共享内存/设备/电源模型属于信任基础；模型通过一致性测试只能提升信心，并不能形式化保证匹配真实硅片行为。
4. **内存模型只覆盖 TSO**：虽然 TSO 覆盖了 RISC-V 的 Ztso 扩展和部分常见处理器行为，但没有覆盖 RVWMO 的所有弱内存行为，也未建模独立的指令缓存（RISC-V 允许非缓存一致性的 icache）。
5. **Sail 模型的过度具体化**：如将 TLB 具体建模为 64 项直接映射缓存，可能限制模型所允许的行为集合（该差异被 conformance test 检测到但未修复）；CLINT 只允许 HART 0 访问等已知限制。

## 摘要
大语言模型（LLMs）在软件开发中的应用日益广泛，但其在复杂硬件设计中的使用仍然有限。这一差距源于公开硬件训练数据的稀缺，以及硬件设计所采用的根本不同的方法论。特别是，将LLMs应用于硬件不仅需要直接的RTL生成：模型必须理解模块边界、模块间连接和验证要求。在本文中，我们提出了一种基于LLM的硬件开发框架，该框架结合了分层中间表示（IRs）和端到端多智能体工作流。核心思想是通过两种结构化IR向LLMs提供硬件设计的抽象：架构草图（Architectural Sketch）——捕获模块拓扑与互连，以及操作规范（Operational Specification）——定义各模块的功能与接口。我们的框架利用这些IR将复杂设计分解为子模块，指定每个模块的功能，并推导出每个模块应如何测试和验证。我们在框架中集成了多智能体调试循环，使智能体能够获取错误反馈并控制调试细节，例如用于仿真的探测信号。我们在Verilog-Eval基准上评估了该框架，实现了95.5%的pass@5率，超越了当前最先进的LLM生成框架。为更好评估在复杂实际设计上的性能，我们引入了一个新的案例研究，涵盖从通用处理器到数字信号处理系统的应用。实验结果表明，此类复杂设计超出了现有方法的能力，而我们的框架是唯一能产生功能性端到端设计的框架。我们生成的RTL遵循所有行业标准设计规则，lint检查干净，功能正确且完全可综合。

## Abstract
Large language models (LLMs) are increasingly used in software development, but their use in complex hardware design remains limited. This gap stems from both the scarcity of public hardware training data and the fundamentally different methodologies used in hardware design. In particular, applying LLMs to hardware requires more than direct RTL generation: the model must understand module boundaries, inter-module connections, and verification requirements. In this paper, we present an LLM-based hardware development framework with hierarchical intermediate representations (IRs) and an end-to-end multi-agent workflow. The core idea is to provide an abstraction of hardware design to LLMs through two structured IRs: Architectural Sketch, which captures module topology and interconnection, and Operational Specification, which defines per-module functionality and interfaces. Our framework uses these IRs to decompose a complex design into sub-modules, specify the per-block functionality, and derive how each module should be tested and verified. We incorporate a multi-agent debug loop in the framework, allowing agents to get the error feedback and control the debug details such as the signals to be probed for simulation. We evaluate our framework on Verilog-Eval benchmark, achieving a pass@5 rate of 95.5%, which surpasses current state-of-the-art LLM generation frameworks. To better assess performance on complex, realistic designs, we introduce a new case study spanning applications from general-purpose processors to digital signal processing systems. Experimental results indicate that such complex designs exceed the capabilities of existing approaches, whereas our framework is the only one capable of producing functional end-to-end design. Our generated RTL follows all industry-standard design rules, is lint-clean, functionally correct and fully synthesizable.

  - **方法论差异**：硬件设计不同于软件——它不仅要生成代码，还需要理解模块边界、模块间互连关系以及验证需求。
- 现有LLM辅助硬件设计研究（Verilog-Eval、RTLLM等基准上的工作）大多局限于**小型、单模块**的设计，而真实世界的硬件设计通常是**多模块、层次化、需要自建testbench**的复杂系统。
- 当前缺乏一个端到端的、可处理复杂层次化系统的LLM硬件设计流程——能够自动完成设计需求分析、任务分解、模块生成、测试台构建、验证调试，并最终交付功能正确的完整硬件系统。

**核心问题：**
> 如何让LLM从高层设计需求出发，自动生成功能正确、可综合的复杂层次化硬件系统？

## 2. 论文提出的方法论

### 核心思想

提出一个**基于分层中间表示（Hierarchical IRs）+ 端到端多智能体框架**的LLM硬件开发方法。核心是：不要直接让LLM写完整RTL，而是先通过结构化IR将复杂设计"拆解+规范化"，再逐层生成和验证。

### 技术细节

#### （1）两种分层中间表示（IRs）

- **Architectural Sketch（架构草图）**：
  - 由 Architecture Designer 智能体生成，采用JSON格式。
  - 捕获**模块层次结构、实例名称、信号连接、端口宽度**等结构信息。
  - 定义了统一的握手协议（in_valid / out_valid）描述数据通路。
  - 不包含功能语义——不描述各模块如何计算，仅描述拓扑和连接。
  - 论文示例：CNN加速器的架构草图描述了 Conv2D → ReLU → Maxpool2D → Flatten → Linear 的串行流水连接，以及各信号的流向和位宽。

- **Operational Specification（操作规范）**：
  - 由 Function Decomposer 智能体生成，基于Architectural Sketch，采用JSON格式。
  - 从**操作视角**描述每个模块的功能：列出所有操作，并为每个操作指定：
    - 模块header（完整Verilog端口接口）
    - 操作名称
    - 流控信号（如 `cmd == 2'b11 && in_valid` 等精确触发条件）
    - 输入模式（单周期/多拍流式，包含端口名、位宽、节拍数）
    - 输出模式（结果格式和输出机制）
    - 功能文字描述
  - 规格是**层次化的**：顶层模块的操作被分解为各子模块实例对应的子操作。
  - 同时生成每个模块的**软件参考函数**（`output = F(input)`），用于构建测试台。

#### （2）端到端多智能体框架（两个阶段）

- **规划阶段（Planning Stage）**：
  - 输入：框图 + 文本设计规格（无需人类介入）。
  - Architecture Designer → 生成 Architectural Sketch。
  - Function Decomposer → 基于Sketch生成各子模块和顶层模块的 Operational Specification + 软件参考函数。

- **生成阶段（Generation Stage）**：
  - 采用**自底向上的方式**：先生成并验证所有子模块，再集成顶层模块。
  - 每个子模块只需对应的 Operational Specification 即可独立生成RTL并验证。
  - 顶层模块利用 Architectural Sketch + 其Operational Specification + 已验证的子模块RTL进行构建。
  - 测试台自动生成：从 Operational Specification 提取输入输出模式，从 Function Decomposer 获取软件参考函数，生成确定性测试台而非纯LLM生成，避免了LLM测试台可靠性不足的问题。
  - 验证按操作逐一进行，层次化测试台调用对应的层次化软件参考函数。

#### （3）多智能体调试循环（Multi-Agent Debug Loop）

针对传统"vanilla self-reflection loop"的两个关键缺陷——（a）仅靠输出不匹配无法定位复杂内部错误；（b）独立迭代导致重复犯错——提出增强的调试机制：

- **语法错误**：直接送RTL和错误回生成LLM修复。
- **功能错误**（多智能体循环）：
  1. **Probing Info Generator（探针信息生成器）**：识别需要监控的关键内部信号（模拟人类工程师的做法）。
  2. **自动化脚本**：在testbench中加入信号观测，逐周期记录变化值。
  3. **Debug Advisor（调试顾问）**：结合IR、RTL、执行轨迹和错误信息，分析根因并生成针对性调试建议。
  4. **Error Fixer（错误修复器）**：根据建议修改RTL。
  5. **Debug History（调试历史）**：维护跨迭代的错误模式、建议和修改记录，防止重复错误。

## 6. 论文的主要结论与发现

- **Verilog-Eval**：本框架（GPT-5）达到 **149/155（Pass@5）**，优于Native GPT-5和MAGE的146/155，且失败案例是Native失败的严格子集，证明Operational Specification能稳定提升RTL生成质量。排除7个本身有问题的案例后，**通过率达到100%**。
- **复杂案例研究**：本框架在7个复杂设计上**全部通过**（7/7）；ROME 0/7，MAGE仅1/7。在29个子模块中，本框架 29/29 全部通过，ROME 16/29、MAGE 19/29。
- **多LLM泛化**：4种LLM（GPT-5、GPT-5.4、Claude Sonnet、Claude Opus）分别通过 7/7、7/7、5/7、6/7，证明框架具有较好的LLM无关性；但Claude系在RISC-V和Vector Unit等最复杂用例上失败，说明底层LLM能力仍是瓶颈。
- **消融结果**：
  - 移除Operational Specification后成功率从 7/7 降到 2/7；移除Architectural Sketch后降到 5/7。两者提供互补的功能信息和结构信息。
  - 直接生成（1/7）和直接修复（2/7）即使在更高预算下也远远差于完整框架。
  - 多智能体调试循环在顶层模块上优势显著（7/7 vs vanilla 4/7），尤其是Systolic Array和Vector Unit这类需要内部信号观测的复杂设计。
- **生成规模与质量**：生成的RTL **lint检查干净、功能正确、完全可综合**；平均780行RTL，综合后平均约140万单元（从8K到630万不等），远超Verilog-Eval的平均16行。

## 7. 优点

- **端到端自动化**：从高阶自然语言+框图到完整的、可综合的、已验证的硬件系统，全程无需人工编写testbench或干预调试，远超现有框架（对比框架要么依赖人工testbench，要么只支持单模块设计）。
- **创新的分层IR设计**：Architectural Sketch和Operational Specification分别捕获结构和功能语义，是论文的核心学术贡献。通过IR将设计意图"结构化"，使LLM能有效地采用分治策略处理复杂系统。Operational Specification将软件参考函数和测试台生成解耦，使验证不再单纯依赖LLM的输出。
- **多智能体调试循环的设计洞察**：通过探针信号选择、周期级轨迹分析、调试历史维护等方式，模拟人类工程师的调试方式，解决vanilla反馈循环在复杂模块中的调试不足。这在顶层模块集成时尤为重要。
- **实验验证严谨**：
  - 在标准基准上验证兼容性（Verilog-Eval 100% clean pass）。
  - 自建了比Verilog-Eval复杂约55倍token、12倍LOC、260倍cell的案例研究，填补现有基准无法评估复杂设计的空白。
  - 对ROME和MAGE失败原因的定性分析深入（如ROME不重读prompt导致无法修复误解、MAGE的judge信任问题等）。
  - 消融实验设计合理，逐一分离了每个组件（两个IR、调试循环）的贡献。
  - 综合到22nm工艺，验证了可综合性。

## 8. 不足与局限

- **案例研究规模有限**：虽然7个设计涵盖了多个领域，但相对于硬件设计空间来说仍很小。未能验证框架在超大规模SoC级设计上的表现。
- **Verilog-Eval 排除标准主观性**：排除的7个"有问题"案例虽有理有据，但数据清洗标准由作者决定；此外未采用Verilog-Eval V2数据集（理由是V2问题更多），这可能削弱说服力。
- **对基线方法的评估条件不完全对称**：ROME和MAGE主实验仅用GPT-5.4评估，未展示其他LLM下的表现差异；也未报告这三种框架在Verilog-Eval上的完整对比（表格中只给了Ours vs MAGE vs Native）。
- **成本与延迟较高**：每个复杂案例约800秒和82K tokens，Vector Unit高达2641秒和194K tokens，实际工程使用中成本和时间开销仍是限制因素。
- **底层LLM的能力天花板**：跨LLM实验中Claude Sonnet和Opus分别在1-2个最复杂案例中失败，说明框架只是放大了基础模型的潜力，并不能无限弥补LLM的推理短板。
- **调试迭代上限的设定**：实验中设定了10次调试迭代的上限，这一上限可能不足以应对某些极其复杂的设计，但对于更复杂的设计能否收敛仍不确定。框架的收敛性保证主要依赖经验和启发式。
- **未涉及PPA优化**：当前框架只保证功能正确，未考虑性能、功耗、面积的优化。作者在Future Work中承认这一点，计划引入物理设计工具反馈来迭代优化。
- **依赖输入的规范性**：输入需要框图+较详细的文本规格，对于用户可以更自然描述的场景（如任意自然语言对话式设计），可能仍需额外的信息提取步骤。

## 摘要
AI 生成的 RTL 验证计划可以满足提供商 schema，却在通往可信执行的边界处失败。我们提出 SecTB-RTL，这是一个可审计框架，涵盖 31 项任务和 124 个自编硬件安全回归。一个确定性的非 AI 基线在不断提高的资源限制下分别杀死了 36、75 和 78 个变异体。首次确认性运行（C1-R2）在模型执行之前失败，因为提供商拒绝了其响应 schema。在未查看结果的情况下仅对 schema 进行修复后，一个单独冻结的后续运行（C1-R3）完成了 1,860 次调用。提供商接受了 1,857 个响应，但只有 9 个通过了生产语义验证器。生成规则与执行规则不匹配。因此，我们将该运行保留为一次工具验证事件，并且不报告任何提示效应估计。该事件表明，提供商或 schema 的接受并不能确立执行有效性。编译和覆盖率只是诊断指标；所保存的精确制品必须通过完整生产路径。随后的一次后续运行被排除，因为它未满足预注册的证据完整性门槛，仅被视为未来工作。我们发布了该基准、保留失败的契约、事件溯源以及所需的治理控制，以防止将基础设施行为误报为模型行为。

## Abstract
AI-generated RTL verification plans can satisfy a provider schema yet fail at the boundary to trusted execution. We present SecTB-RTL, an auditable framework covering 31 tasks and 124 authored hardware-security regressions. A deterministic non-AI baseline killed 36, 75, and 78 mutants at increasing resource limits. The first confirmatory run (C1-R2) failed before model execution because the provider rejected its response schema. After a schema-only repair made without viewing outcomes, a separately frozen follow-up run (C1-R3) completed 1,860 calls. The provider accepted 1,857 responses, but only nine passed the production semantic validator. The generation and execution rules did not match. We therefore preserve the run as an instrument-validation incident and report no prompt-effect estimate. This incident shows that provider or schema acceptance does not establish execution validity. Compilation and coverage are only diagnostics; the exact saved artifact must pass the full production path. A subsequent follow-up is excluded because it did not satisfy the preregistered evidence-completeness gate and is treated only as future work. We release the benchmark, failure-preserving contract, incident provenance, and governance controls needed to prevent infrastructure behavior from being misreported as model behavior.

# 论文总结：Trust, but Validate the Instrument

## 1. 核心问题与研究背景

- **领域背景**：AI 辅助芯片设计正从"代码补全"走向"生成验证工件"（如 LLM 生成自检 HDL testbench）。这带来一个**信任校准（trust-calibration）问题**：生成物可能通过语法解析、跑通 golden 设计、达到高行覆盖率，却缺乏发现安全属性违规所需的激励（stimulus）或判据（oracle）。
- **核心痛点**：编译通过、golden 运行成功、高覆盖率**均不足以**证明验证计划具备安全检测能力。一个验证工件即使满足供应商 schema，也可能在通往"可信执行"的边界处失效。
- **真正的研究问题**：不是"LLM 能否写出 HDL"，而是"在计及所有失败尝试的协议下，生成的验证器能否提供**可度量的安全证据**"。
- **三个部署层问题（RQ）**：
  - **RQ1 工具损耗**：多少供应商接受的输出能通过生产语义边界？
  - **RQ2 保证边界**：哪些生产语义失败对供应商/schema 接受不可见？fail-closed 生命周期能否阻止其成为科学结论？
  - **RQ3 可达参照**：确定性、结果盲（outcome-blind）的非 AI 刺激基线在固定资源下能达到多少变异体检测率？

## 2. 方法论：SecTB-RTL 框架

- **核心思想**：把"AI 生成验证计划"当作一个**测量工具（instrument）**来审计，强调"生成—执行"链路的每一环都必须被独立校准；任何一环的接受都不能推断下一环有效。
- **基准构造**：
  - 31 个 RTL 任务，分属 16 个 (CWE, root mechanism) 分层（15 个双层 + CWE-1241 单例）。
  - 每个任务预先编写 4 个隐藏安全回归变异体，共 **124 个**，全部通过 7 道资格门：解析编译、接口一致、可综合、合法见证激活、形式化非等价、可信回放、两两形式化区分。
- **受限 JSON DSL 契约（sectb-stimulus-v1）**：
  - 必含 `dsl_version`、`test_name`、4–128 个有序步骤；允许复位赋值、顶层驱动、有界 tick（1–16）、输出断言。
  - **禁止**：随机源、循环/分支、层次访问、force、DPI、文件 I/O、模型自定 verdict。
- **提示臂设计**：F0（功能目标）、FC（等注意力功能对照）、SA（抽象安全上下文）、SE（显式安全需求）。主对比 SE−FC，次对比 SA−FC、FC−F0。
- **fail-closed 保证契约**：门控覆盖供应商接受、schema、生产语义、渲染、双仿真器一致、golden 有效性、变异体检测；用加密哈希锁定冻结文件，限制事后修补或重试。
- **统计公式**（文字说明）：
  - `K_tjarm`：任务 t、模型 j、臂 a、重复 r、变异体 m 下，仅当响应合规 + 双仿真器 golden 通过 + 杀死变异体时取 1。
  - `Ȳ_t,a`：对 3 模型 × 5 重复 × 4 变异体求均值。
  - `θ(a)`：31 个任务的宏平均（task-macro）。
  - `Δ = θ(SE) − θ(FC)`：主对比效应。
  - 统计单元为**任务（n=31）**，模型/重复/变异体嵌套其中；用按任务重采样的 bootstrap。
- **漏斗（funnel）**：scheduled → response/schema → compile → golden-valid → conclusive execution → kill。所有失败保留在分母中。

## 3. 实验设计

- **数据集/场景**：构建框源自 **HardSecBench revision e2084be7**；任务为有目的筛选（非概率抽样）。对模型输入做 alpha 重命名、去注释的 golden RTL、功能需求、端口契约、输出 schema、token 预算、执行契约。模型**从不**看到变异体 RTL、diff、见证迹、隐藏官方测试或变异结果。
- **Benchmark**：SecTB-RTL，31 任务 / 16 分层 / 124 变异体。
- **对比方法/条件**：

## 5. 实验数量与充分性

- **实验规模**：C1-R3 完成 465 块 × 4 臂 = 1,860 次调用、7,440 条变异体行；基线在 3 档预算下覆盖全部 124 个变异体。
- **充分性**：
  - 变异体资格化（7 道门）和任务筛选（C1–C7 检查）较扎实，31/31 通过跨臂字节一致性检查。
  - 但**确认性处理实验未达到可分析终点**：R2 因 schema 被拒（8 次尝试无模型响应），R3 虽完成调度却因生成/执行语义不匹配，仅 9/1,860（0.48%）通过生产语义校验。
- **客观性与公平性**：
  - 采用预注册（preregistration）、固定种子、独立随机化调用顺序、禁止重试/重抽、结果盲修复。
  - 然而预注册是**作者自封（author-sealed）而非独立评审**，存在自我审计偏差风险。
- **结论**：在"工具校准"意义上证据充分（事故证据完整保留），但在"提示效应估计"意义上**不充分**——论文明确拒绝报告任何处理效应。

## 6. 主要结论与发现

- **核心发现**：供应商/schema 接受（1,857/1,860 = 99.84%）**不等于**执行有效性（9/1,860 = 0.48%）。1,848 次调用缺口被定位为：执行层强制了复位状态机规则，而生成侧契约与 schema 探针未包含该规则——**连探针自身的规范响应都未通过后续生产规则**。
- **基线结论**：非 AI 基线在 32/64/128 步分别杀死 36/75/78 个变异体，task-macro 产出为 0.290 / 0.605 / 0.629；64→128 步的增益远小于 32→64 步，说明**单纯加长通用刺激不能替代安全专属的激活与判据**。
- **测量学结论**：编译与覆盖率只是**下游诊断**，不能替代对齐的语义契约；只有**精确持久化的工件**（而非内存中的前体）通过完整生产路径，才能进入安全决策。
- **治理结论**：fail-closed 生命周期阻止了把基础设施行为误报为模型行为，代价是放弃了一个处理效应结果，但换来了结论的可靠性。
- **责任性结论**：负责任的结果是"负面但具体"——证明了测量链在何处失效、如何被检测、以及哪些控制可防止无依据的模型性能声明。

## 7. 优点

- **方法论创新**：首次将"AI 生成 RTL 验证计划"系统性地当作**测量工具**审计，把评估重心从"生成质量"转向"测量链有效性"。
- **fail-closed 与事故保留**：不把失败案例包装成成功，完整保留 R1–R3 血统，事故 manifest 与确认性证据严格分离。
- **预注册严谨性**：任务注册表、变异体、提示、schema、调度、评分、分析规则全部在接触供应商前冻结；用加密哈希保证工作树不变。
- **分层审计意识**：明确列出 provider → schema → semantic contract → renderer → persistence → resume replay → golden validation → mutant oracle 八道边界，每道需独立探测器。
- **治理控制表（Table III）** 将失效边界、检测方法与治理措施一一对应，具有很强的工程可操作性。
- **诚实的负面报告**：明确声明不主张"首个 LLM 硬件安全验证计划"、不主张安全提示普遍提升、不主张防漏洞或流片后安全性。

## 8. 不足与局限

- **无处理效应估计**：核心确认性实验因工具不匹配而失败，论文无法给出 SE−FC 等提示效应的任何数值结论。
- **构念效度**：变异体是**自编的受控回归代理**，不是真实生产漏洞利用；杀死的变异体不必然对应可被利用的芯片缺陷。
- **外部效度有限**：结论仅限公开 RTL、自编回归、**单一供应商接口、3 个模型别名、固定日期、受限 DSL**，不是通用的模型排名。
- **预注册非独立评审**：作者自封（author-sealed），存在自我审计偏差风险。
- **资源信息缺失**：未披露 GPU/训练算力、token 总量、费用等，削弱了可复现的成本评估。
- **后续实验被排除**：未满足证据完整性门控的后续运行被排除，仅作为未来工作，意味着当前证据基础是"事故 + 基线"而非"完整确认性研究"。
- **应用限制**：不覆盖物理攻击、模拟泄漏、布局布线后行为、门级时序、代工厂威胁或硅后验证；不涉及综合、物理实现到现场部署的安全保持。
